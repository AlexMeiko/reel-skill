> ⚠️ **本目录已于 2026-09-24 精简**：`variants/`、`qa/`、`probe/`、`evidence/`、`table/` 已按使用者决定删除，

**一句话**：一张黄昏湖景先以 64px 粗马赛克整幅出现，240 个色块按各自的时刻逐级收敛
（64→32→16→8→4→2→1px），露出清晰画面；清晰瞬间有一次轻微过冲，随后缓慢推近并定格。

- `index.html` 主方案（canvas 平均色金字塔 + `hash(块坐标)` 决定逐块收敛时刻）
- `out.mp4` 成片：1280×720 / 30fps / 5.000s / 150 帧
- `sheet.png` 15 格 contact sheet；`qa/qa-00..04.png` 成片抽帧
- `probe-mp4/` 按你要求的 `0 / 1.5 / 2.5 / 3.5 / 4.96`s 从**成片**抽的五帧（亲眼看图用）
- `variants/` 两个备选实现（见 `variants/README.md`）

## 1. 本特效的命门：清晰时刻 = `hash(块坐标)`，不是 `hash(帧号)`

画面在 `load` 时算一张 **240 个基块（20×12，每块 64px）的次序表 `U[]`**，
之后每帧只做一件事：`lv = 6 - floor(6 * span(t, tc, tc+DUR))`，`tc = T0 + SPREAD * U[i]`。

```js
/* 块次序：对角前沿（保证「成片推进」）+ fBm 噪声（保证团块边缘不规则）。两者都只是坐标的函数 */
function cellU(cx, cy) {
  var front = 0.58 * (cx / (NC - 1)) + 0.42 * (cy / (NR - 1)); // 左上 -> 右下
  return 0.60 * front + 0.40 * fbm(cx, cy);                     // fbm = 3 个八度的 hash 值噪声
}
/* 归一化后写进 U[]，只算一次、缓存 */

function reelDraw(t) {
  for (cy…) for (cx…) {
    var tc = T0 + SPREAD * U[cy * NC + cx];        // 这一块的起手时刻：常数表查表
    var u2 = reel.span(t, tc, tc + DUR);
    var lv = MAXLV - Math.floor(MAXLV * u2 + 1e-9); // 7 档阶梯，块边长 2^lv
    lg.drawImage(pyr[lv], cx * (64 >> lv), cy * (64 >> lv), 64 >> lv, 64 >> lv,
                 cx * 64, cy * 64, 64, 64);         // 查表 + 全量重绘，不留上一帧状态
  }
}
```

### 为什么不是 `hash(帧号)`

| 维度 | `hash(块坐标)`（本实现） | `hash(帧号)`（「每帧随机挑几个块变清晰」） |
|---|---|---|
| 收敛是否可证明 | **构造保证**：`spread` 按 `T_REVEAL` 反推，最后一块在 `t=3.30` 恰好到 1px；`t≥3.30` 全清晰是恒等式 | 概率事件。240 块、每帧抽 8 块、到 1.8s 只有约 46 帧，尾部必然有没被抽中的块 —— 「末帧还有残留模糊块」是设计上无法排除的 |
| 单调性 | 每块一条只降不升的 LOD 曲线，不会清晰了又糊回去 | 每帧独立抽样，上一帧清晰的块这一帧可能不在抽样里 → **回退成粗块，全屏闪烁** |
| 是不是 `t` 的函数 | 是。`U` 与 fps、与调用次数、与到达路径都无关 | 不是严格成立：`帧号 = floor(t*fps)`，同一个 `t` 在 30fps 与 60fps 下帧号不同 → 画面不同 |
| 空间形态 | 前沿 + fBm → 团块宽 4~5 格（≈300px）的**成片推进**，边界不规则但不碎 | 抽样掩码是白噪声 → 永远「均匀撒胡椒面」 |
| 换 seek 路径（verify 的致命盲区补丁） | 通过：不存任何集合 | **最容易被抓的写法**是「每帧挑几块，把块号塞进 `Set`/累加器」。它每次按同一顺序 seek 同一批 `t`，拿到相同调用次数，所以能过「同一 t 截两次」，但过不了换路径检查：直接 seek 到 2.5 与先经 0/1.25 再到 2.5，累加器里的集合不同 |

一句话：`hash(帧号)` 把「谁变清晰」交给**时间轴的第几次滴答**，
而 seek 架构下「第几次滴答」根本不是一个稳定的量；`hash(块坐标)` 把这件事交还给**块自己的身份**，
于是它天然是 `t` 的纯函数，而且天然单调、天然可证收敛。
（本次 当时的机器验收 的三条确定性检查全绿，其中「换 seek 路径同一 t 仍逐字节一致」就是对这一条的客观背书。）

## 2. 平均色金字塔：构建与查表

```js
pyr[0] = src;                                   // 源图 1280×768
for (var lv = 1; lv <= 6; lv++) {
  var s = 1 << lv;
  var c = document.createElement("canvas");
  c.width = SW / s; c.height = SH / s;          // 20×12 … 640×384，整除
  var g = c.getContext("2d");
  g.imageSmoothingEnabled = true; g.imageSmoothingQuality = "high";
  g.drawImage(src, 0, 0, SW, SH, 0, 0, c.width, c.height);   // 一次降采样 = 面积平均
  pyr[lv] = c;
}
```

- **构建时机**：第一次 `reelDraw` 时（`ensureBuilt()`）一次性建好并缓存。`pyr` 与 `U` 都是纯常量，
  绝不逐帧重生成 —— 这正是 SPEC 那条「块掩码/金字塔必须在 load 时生成并缓存」的落实。
- **查表**：`drawImage(pyr[lv], 源格坐标, 目标 64×64, imageSmoothingEnabled=false)`。
  因为 `SW/s`、`SH/s` 都整除，`sx = cx*(64>>lv)` 是整数，每档的块边长正好是 2 的幂；
  且 `lv=0` 时是 `pyr[0]` 的逐像素恒等拷贝 —— **末帧的画面就是源图本身，没有任何重采样模糊**。
- **成本**：7 张 canvas 共约 1.31M 像素（983040+245760+61440+15360+3840+960+240）；运行时每帧 240 次 `drawImage`（全量重绘，无脏矩形）。

## 3. 源图为什么必须程序化生成

lint 禁 `<link href>` / `<script src>` / `@font-face`，所以不能引用任何外部 PNG/JPG/字体；
而且源图必须是「`t` 无关的常量」——它一旦依赖加载时机，双截帧就会不一致。
因此画面用 canvas 画出来（渐变天空 + 落日 + 两道山脊 + 湖面倒影 + 岸与松树 + 归鸟 +
确定性星点 + 暗角 + LCG 胶片颗粒），在 `load` 时画一次、缓存成 `pyr[0]`。
星点/波纹/松树位置全部来自 `hash(i)`，没有一处 `Math.random()`。

## 4. 三方案对比

| | 主方案 `index.html` | `variant-a.html` | `variant-b.html` |
|---|---|---|---|
| 谁来画粗块 | canvas 金字塔，每帧全量重绘 240 格 | 4 张 canvas（20×12 / 80×48 / 320×192 / 1280×768）CSS 放大，`image-rendering: pixelated` | 1 张 64px 粗块 `<image>` + 1 张 1:1 `<image>` |
| 清晰时刻的粒度 | **每块 64px 各自 7 级阶梯**（240 条独立曲线） | 按 64px 行推进，前沿是 16px→4px→1:1 的三段**阶梯带** | 每 8px 细格一次 `fill-opacity` 淡入（次序继承 64px 基块 + 细格微抖） |
| 前沿形态 | 团块宽 4~5 格的二维波 | 逐行左→右的**单调阶梯**（`clip-path` 只能表达简单区域） | 同主方案的二维波，但过渡是**叠影淡入**而不是「聚焦」 |
| 每帧写入量 | 240 次 `drawImage` | 3 条 `clip-path` 字符串 + 1 个 `transform` | 15360 次 `fill-opacity` |
| 一次性成本 | 7 张金字塔 + 源图 | 同主方案 + 4 张降采样 | 同主方案 + 1 张 `toDataURL` + 15360 个 `<rect>` |
| 观感 | **最像「马赛克在收敛」**：块边缘硬、阶梯清楚 | 干净、块感强，但前沿是直线阶梯，没有「随机团块」 | 柔、有显影感，但中间态是半透明叠影 |
| 复用性 | 差一点：`U` 与像素金字塔绑在 canvas 上 | **最好**：把 4 张 canvas 换成 4 张任何图都能用 | 一般：mask 里的 rect 数量写死在 DOM |
| 成片体积 | 1172KB | 1154KB | 1339KB |
| 实测密度 | 最长静止 0.50s（15 帧）/ 静止占比 13% | 0.40s（12 帧）/ 16% | 0.53s（16 帧）/ 17% |
| verify | **0 FAIL / 0 WARN** | 0 FAIL / 1 WARN（文件名不是 `index.html`） | 0 FAIL / 1 WARN（同上） |

**推荐主方案。** 理由：只有它能给「每一个块」一条独立的 7 级阶梯曲线 ——
这才是这个特效要证明的东西（清晰时刻是块坐标的函数），而且末帧是金字塔 `lv=0` 的恒等拷贝，
每个块都有确定无疑的清晰态。variant-a 最省事也最好复用，但它把「逐块」退化成「逐行」，
前沿是几何直线而不是噪声团块；variant-b 的代价最大而收益最小，详见下节。

### variant-b 的元素数量代价（实测，不是估算）

SPEC 里算的是 8px 网格 ≈ 14400 个 rect。第一版按最直觉的写法做：**每个 rect
`fill="url(#p-sharp)"`（`<pattern>` 贴 1280×768 原图）+ 逐帧改 `opacity`**。
结果直接跑不出来：

```
Error: cdp timeout: Page.captureScreenshot
    at Timeout._onTimeout (file://<技能目录>/tools/capture.mjs:222:16)
```

- 15360 个 pattern rect：**第 2 帧起 `Page.captureScreenshot` 超过 20s 上限**（第 1 帧能出，因为 opacity 还没变过）。
- 降到 16px（3840 个 pattern rect）：**仍然超时**。
- 根因是 `<pattern>` 本身，不是元素个数：每个 rect 都要把 1280×768 的 pattern 贴图重栅格化一遍。
- 改成**一张 1:1 `<image>` + `<mask>` 里 15360 个白 rect 改 `fill-opacity`** 之后，
  4 张静帧（含浏览器启动）15.3s、整片 150 帧正常导出 —— 这一次原图只解码/栅格化一次。

结论：在「逐块贴原图」这个需求下，SVG 的元素数量代价不是线性的，
**pattern 填充会把 1.5 万个 rect 变成 1.5 万次整图栅格化**；要留在 SVG 里就得改成 mask。
即便如此，每帧 15360 次属性写入仍比主方案的 240 次 `drawImage` 重两个数量级，
所以主方案胜出。

## 5. 踩坑记录（都是实际发生并修掉的）

1. **湖面反光留下一条硬边矩形**。第一版用竖向 `createLinearGradient` + `fillRect(SX-130, 454, 260, 252)`
   画日晕，线性渐变只在 y 方向衰减、x 方向是硬切边，于是在成片上出现一块
   x≈732…992、y≈454…706 的**比周围亮的矩形**（`qa` 上一眼就能看到，t=1.0 时最明显）。
   改成「`save/translate(SX,486)/scale(1,1.95)` + 径向渐变 + 大一圈的填充」后消失。
   > 教训：`fillRect` + 单向渐变 = 另外两个方向必然是硬边。
2. **反光像条形码**。第一版倒影是 46 条等距、宽度随机的硬边横条，缩略图上像一摞条形码。
   改成「软晕 + 62 条越远越宽、越散、越淡的圆头短线 + 14 条短亮芯」，才是水面粼光。
3. **variant-b 的 `<pattern>` 超时**（原文见上节）。
4. **场景内仪表读错**。variant-a 的「块尺寸」一开始取的是 `max(前沿)`，
   于是**跑得最快的那一行**让读数提前跳到 `1px`，而屏幕上明明还有 64px 块。
   改成 `min(前沿)`：「屏幕上还看得见的最粗块」由**最落后的那一行**决定。
5. **`Math.round(0.996*100)===100`**：两个变体的百分比在未完成时夹到 99%（PATTERNS §6.2），
   主方案不用百分比，直接用「已到 1px 的块数 / 240」，天然没有这个问题。
6. **仪表分母不能用 `t/duration`**：末帧是 `149/30 = 4.9667s`，用 duration 当分母永远停在 99.3%。
   主方案的仪表分母是「块数」，`T_REVEAL = 3.30` 是字面量常量，`t≥3.30` 必然 240/240。
7. **【返工】主次颠倒**：第一版揭示只占全片 38%（`T_REVEAL = 1.78`），
   评审用 Sobel 边缘能量逐帧量出「0→1.9s 就揭示完，之后 3 秒只剩推近，Sobel 从 1.8s 起就是一条平线」，
   且 sheet 上第 6–14 格（9/15）几乎一模一样。修法**只动时间轴、不动机制**（`U` 的形状、对角前沿 + fBm、
   逐块 7 级阶梯一行未改）：
   - `T_REVEAL` 1.78 → **3.30**，于是 `SPREAD = T_REVEAL - T0 - DUR` 0.98 → **2.50**，揭示段占全片 61%；
   - 推近 `T_PUSH1` 4.68 → **4.83**、`T_PUSH0` 改为 `T_CLEAR`，倍率 `0.10` → **0.16**（≈3.6%/s → **10.5%/s**）；
   - 过冲窗口 `T_POP1` 由 `T_CLEAR + 0.60` 压到 `T_CLEAR + 0.22`，否则推近会被挤到 3.90s 才开始。
   返工后 Sobel 曲线单调升到 **t=3.30s 才到顶**，逐帧 `YAVG` 在推近段 0.7~1.7（噪声地板 0.005），
   末帧仍是 `240/240 · 1px`。

## 8. 两个场景内仪表的自洽

主方案 HUD 的两个数：`清晰块 n/240` 与 `最粗块 64→1px`，
**都是在同一个 `for (cy) for (cx)` 循环里、用同一个 `lv` 数出来的**（`clearN` 与 `maxLv`），
不存在第二条时间线：

```js
if (lv === 0) clearN++; else if (lv > maxLv) maxLv = lv;
```

- 文案与数字同源：`n=240 ⟺ maxLv=0`（一块不清就不可能出现 `1px`）。
- 末帧必到终点：分母是块数、`T_REVEAL` 是字面量常量，`t≥3.30` 恒为 `240/240` 与 `1px`。
- 一个特效只有一个「开始/结束时刻」：`T0 / T_REVEAL / T_CLEAR / T_PUSH0 / T_PUSH1` 全部是模块顶部的字面量。

> **若以后把多个特效 concat 成整片**：这个 HUD 是画在 canvas 里的场景内仪表，
> 会和 kit 的 `gbar.json` 底栏抢画面。届时应删掉 HUD（或改成 kit 的 `hud` 通道 +
> `REEL.offset`），否则两条进度指示会同时出现在画面里。

时间轴（全部是字面量常量，见 `index.html` 顶部）：

| 时间 | 事件 |
|---|---|
| 0.00–0.26 | 全糊静置壳（240 块全 64px，HUD `0/240 · 64px`） |
| 0.26–3.30 | 逐块 7 级阶梯收敛（`tc = 0.26 + 2.50 * U[i]`，单块耗时 0.54s）—— 全片主体，占 61% |

| 3.32–4.83 | 推近（scale 1.000 → 1.160，约 10.5%/s，同时 -8px 位移）—— 与过冲同起点，按 `(1+pop)·(1+0.16·push)` 相乘 |
| 4.83–5.00 | 定格结束帧（末帧 t = 4.9667 → 仪表 `240/240 · 1px`） |

> 推近曲线是 `easeInOut`，起始 0.1s 位移很小，过冲正好填满这一段，观感仍是「过冲一下 → 缓推 → 定格」。
