**一句话**：一行标题先是一整排乱码，随后从左到右逐字「解码」成真字；未解码的字符每 1/12 秒
换一次乱码，已解码的字符落位时带一次衰减的过冲弹跳。

```
index.html            主方案：时间量子 + 三级字符池（浅纸「档案」皮）
out.mp4               主方案成片 1280×720 / 30fps / 5.0s / 150 帧
qa/                   capture 抽帧（t = 0 / 1.25 / 2.5 / 3.75 / 5.0）
sheet.png             verify 生成的 5×3 contact sheet（一张图看全片）
variants/variant-a.html / variant-a.mp4   码点区间扫描（深色「频谱」皮）
variants/variant-b.html / variant-b.mp4   主方案 + 方块光标 + 扫描亮带
```

时间轴（三方案一致，`t` 秒）：

| 段 | 区间 | 画面 |
|---|---|---|
| 静态壳 | 0 – 0.45 | 完整壳（框、页眉、页脚、下划线轨道）已就位；整行 16 字全是乱码；无光标 |
| 解码 | 0.45 – 3.60 | 字符 `i` 在 `0.45 + i×0.21` 锁定；前沿到下划线右端 |
| 落位 | 3.60 – 4.15 | 最后几个字做衰减弹跳，前沿填满 |
| 静止 | 4.15 – 5.00 | 结束态：全行真字 + 满格下划线 + `LOCKED 100%` |

## 1. 常见写法为什么在本 skill 里会坏

| 常见写法 | 坏在哪 | 本 skill 的 seekable 改法 |
|---|---|---|
| `Math.random()` 每帧给乱码换字 | `t=0.5` 截两次得到两张不同的图；当时的机器验收 的确定性检查直接 FAIL（同一 `t` 两次截帧必须逐字节一致）。而且它连「同一帧」都不稳：同一帧被渲染两次都不一样 | 换字频率绑到**时间量子** `q = Math.floor(t*12)`，字符由 `hash(i, q)` 纯函数决定；`q` 相同 ⇒ 逐字节相同 |
| `setInterval(() => scramble(), 83)` | 定时器是墙钟，`__reelSeek(t)` 不会重放它；截帧脚本 seek 到 2.5s 时画面可能停在第 3 次 tick 的状态。lint 直接禁用 | 同上：`Math.floor(t*12)` 就是从 `t` 推出来的 tick 序号，没有独立时钟 |
| 无时钟 `requestAnimationFrame` 累加 `dt` | 累加器让结果依赖「跑了几帧」，掉帧就变样；seek 不可复现 | 删掉累加器，所有量都是 `f(t)`；要 rAF 只读 `window.__reelTime` |
| `transition: color .3s` 当落位动画 | `transition` 由浏览器时钟驱动，`__reelSeek` 只 `pause()`/设 `currentTime`，seek 后停在过渡中间态且不可复现 | 落位弹跳写成解析式 `osc(p)`（见 §2），每帧直接算最终值 |
| `animation: blink 1s infinite` 做光标闪烁 | `infinite` 被 lint 禁；而且 CSS 动画与 `reelDraw` 是两条独立时间线，seek 后两者不同步 | 方波也写成 `t` 的函数：`Math.floor(t*6) % 2 === 0` |
| 逐字解码用 `setTimeout` 排 16 个定时器 | 同上，seek 到 2.5s 时可能只有前 3 个定时器跑过；`setTimeout` 也不在允许列表里 | `lock_i = T0 + i×STEP`，每帧比较 `t < lock_i` 决定该字是乱码还是真字 |
| 乱码字符池直接用 `Array.sort(() => Math.random()-0.5)` 打散 | 打散结果每次运行不同，字符池本身都不确定 | 池是字面量常量，取哪个由 `hash()` 决定 |
| 「CSS 动下划线 + JS 动百分比」两条线 | 同一量两个真值来源，seek 后两者对不上（比如条 67%、数字 71%） | 只在 `reelDraw(t)` 里算一次 `front`，下划线宽度和百分比都从它派生（§2 第 3 点） |

## 2. 关键技术点

### (1) 时间量子：乱码节拍 = `t` 的纯函数

```js
function hash(i) {                 // 确定性伪随机：同一 i 永远同一结果
  var x = Math.sin(i * 127.1 + 311.7) * 43758.5453123;
  return x - Math.floor(x);
}
// 每个字符每 1/12 秒换一次乱码；q 只由 t 决定，与「渲染了几帧」无关
var q = Math.floor(t * 12);
var idx = Math.floor(hash(i * 91.7 + q * 3.1 + lvl * 13.7) * pool.length);
```

`q` 是整数 tick 号：`t=2.500` 永远得到 `q=30`，所以 seek 到同一时刻必得同一张图。
它还有两个副作用是白拿的：

- **掉帧不变样**：12 Hz 的量子 = 0.0833s = 2.5 帧（30fps）。相邻两帧可能落在同一量子内，
  此时画面**故意**完全一样 —— 这正是「节拍」的观感；导出掉一帧也不会让乱码提前或延后。
- **量子频率不能取 30/60 Hz**：与帧率同频时每个量子只占 1 帧，闪烁退化成逐帧噪声，看不清节拍；
  取 12 Hz 让每个量子跨 2.5 帧，人眼能数出「咔咔咔」的换字感。

### (2) 三级收敛的字符池

```js
var POOLS = [
  "\u259A\u259E\u2588\u2593\u2592\u2591\u2596\u2597\u2598\u259D", // 0 全角块：▚▞█▓▒░▖▗▘▝
  "<>/\\|#$%&@*+=~^?!",                                            // 1 ASCII 信号
  "\u7684\u4E00\u662F\u4E0D\u4E86\u5728\u4EBA\u6709\u6211\u4ED6\u8FD9\u4E3A\u4E4B\u5927\u6765\u4EE5\u4E2A\u4E2D\u4E0A\u4EEC\u5230\u8BF4\u56FD" // 2 汉字假字
];
var TH = [1.0, 0.3];   // 离锁定还剩 rem 秒：>1.0 用池 0，>0.3 用池 1，否则用池 2
```

用**绝对剩余时间**（而不是「自己寿命的百分比」）分档，是为了让整行出现一条横向的
**收敛梯度**：t=2.5s 时左半是真字、中间是汉字假字、再往右是 ASCII 符号、最右是全角块 ——
观众一眼就能看出「解码前沿在哪、信号强度往右递减」。如果按各自寿命分档，每个字都停在
自己那一档，整行会变成均匀噪声，反而看不出前沿。

三档的**视觉宽度也递减**：全角块 1em → ASCII 半角 → 汉字 1em。因为每格固定 1em 居中
（见 §3 踩坑 2），宽度变化只体现为「格子里的东西变小了」，不会让整行左右抖动。

### (3) 落位弹跳：一个衰减余弦，含过冲

```js
var lock = T0 + i * STEP;                 // 该字的锁定时刻
var p = Math.min(1, (t - lock) / SETTLE); // SETTLE = 0.55s
var osc = p >= 1 ? 0 : -Math.cos(p * Math.PI * 2.2) * Math.exp(-4.5 * p);
el.style.transform = "translateY(" + (7 * osc).toFixed(2) + "px) scale(" +
                     (1 + 0.30 * osc).toFixed(4) + ")";
```

`osc` 在 `p=0` 处等于 `-1`：刚锁定的一瞬间字号只有 0.70、位置高 7px，像「掉」进格子里；
`p≈0.227` 处第一次过零（回到 100%）；`p≈0.455` 处到达**过冲峰** `+0.129`
（`scale ≈ 1.039`、下沉 0.9px）；之后 `exp(-4.5p)` 把振幅压掉，`p=1` 时强制归零。
参数含义：`0.30` = 过冲幅度，`2.2` = 一个落位周期内的振荡次数，`4.5` = 衰减速率
（越大越干脆）。**整个落位是 `p` 的解析函数，没有 transition、没有动画队列**，
所以 seek 到落位中途（比如 t=3.68）也能拿到那一瞬间的正确形状。

同一次插值里还把颜色从朱红 `#c0392b` 线性插到墨色 `#1d1a15`，让「刚解码」有暖色余温。

### (4) 一条时间线只有一个前沿值

```js
window.reelDraw = function (t) {
  var f = (t - T0) / STEP;
  var front = clamp(f + 1, 0, N);                 // 唯一的真值来源（字符数，连续）
  for (var i = 0; i < N; i++) drawChar(i, t);      // 每格只写一次
  fillEl.style.width = (front / N * geo.w).toFixed(2) + "px";   // 下划线宽度
  var pct = Math.round(front / N * 100);                        // 百分比
  statusEl.textContent = t >= T1 ? "LOCKED 100%" : "DECODING " + ("00" + pct).slice(-3) + "%";
};
```

下划线宽度、百分比、`LOCKED` 切换全部从同一个 `front` 派生，不可能对不上。
`t >= T1` 时文案立刻切成 `LOCKED`，避免「100% 还写着 DECODING」的进行态。

## 3. 踩坑记录

1. **SPEC 里的 `0.055s/字` 与「3.6s 到行尾」自相矛盾。** 16 字的标题按 0.055s 走完只要
   `15×0.055 = 0.83s`，前沿 0.83s 就到行尾，和硬性验收的 `t≈3.6` 差了 4 倍多（0.055 显然
   是给 50+ 字的长行写的）。我保留 SPEC 的公式形状 `lock_i = T0 + i×STEP`，但把 `STEP`
   由标题长度反解出来：`STEP = (3.60 - 0.45) / (16 - 1) = 0.21`，这样两个约束同时成立。
   顺带一个副作用值得注意：`STEP(0.21) < SETTLE(0.55)`，所以任何时刻都有约 2.6 个字
   处于「刚解码」的朱红状态 —— 这不是 bug，是刻意的「暖色余温带」。

2. **等宽 CJK 字体里 ASCII 是半角，直接排会左右抖。** `Noto Sans Mono CJK SC` 的汉字是
   1em、ASCII 是 0.5em。如果让每个字符自然占宽，那么字符在「全角块 → ASCII → 汉字」之间
   切换时整行宽度会变化，后面的字会左右横跳（在 contact sheet 上表现为整行在抖）。
   改成**每个字一个固定 1em 的居中格子**：

   ```css
   .ch { display: inline-block; width: 1em; text-align: center; }
   ```

   这同时让 `getBoundingClientRect()` 量出的标题宽度恒等于 `16 × 54px = 864px`，
   **与字体是否已加载无关**，所以下划线的 `left/width` 是稳定的常量，不会因为字体
   加载时机不同而产生两次截帧的亚像素差异。

3. **`t=3.6` 之后如果只是「不动」，末段会浪费。** 第一版里 3.6s 后全行真字、下划线满格，
   于是 `t=3.75` 和 `t=4.995` 两张采样帧会完全相同（当时的机器验收 只查「所有采样帧全等」，
   这种「两张相同」不算 FAIL，但末帧就失去了「结束态」的信息）。改成让状态文案在 `T1`
   从 `DECODING 100%` 切到 `LOCKED`，并让最后几个字的弹跳延续到 4.15s，末段才是真正的
   结束态而不是「停住的中间态」。

4. **乱码池必须逐字确认字体覆盖，不能只看「有没有 fallback」。** 块元素 `▚▞█▓▒░▖▗▘▝`
   容易被误认为需要特殊字体。用 `fc-list ':charset=259a'` 逐个码点查过，`Noto Sans Mono
   CJK SC` 全覆盖（`30a1`/`03b1` 也覆盖），最终在 `sheet.png` 上肉眼确认无豆腐块。
   注意 `fc-list` 的 fallback 会让「有字体渲染」和「渲染成豆腐」看起来一样，
   所以这一步必须看图，不能只看命令输出。

5. **第一次跑 当时的机器验收 是 1 FAIL**：`[FAIL] deliver: 缺 README.md`。
   验收器把 README 当作交付物的一部分（`--no-render` 也查），所以 README 要先写、
   再跑全量验收。除此之外 lint 段 0 WARN（没有任何 CSS animation，全部走 `reelDraw`）。

6. **variant-b 的光标闪烁与 contact sheet 采样同频，发生混叠。**
   光标周期是 `2/6 s = 1/3 s`，而 当时的机器验收 的 sheet 正好是 `15 帧 / 5s = 3fps`，
   采样点落在 `t = 0, 1/3, 2/3, 1, …`，于是每次采样都有 `floor(t*6) % 2 === 0` ——
   `sheet-b.png` 上光标**恒为「亮」**，看起来像一个静止的红框。差点据此误判「方波没生效」。
   改在 `--at 0.5`（相位灭）和 `--at 0.7`（相位亮）两张越采样点的静帧上对比，
   才确认光标确实在按 `t` 闪。教训：**动效频率若与抽帧频率成整数比，contact sheet
   会系统性地骗你**；此时必须挑一个不在采样格点上的 `t` 复验。

## 4. 方案对比

| | 主方案 index.html | variant-a 码点区间 | variant-b 光标 + 扫描带 |
|---|---|---|---|
| 乱码来源 | 3 个字面量字符池，`hash` 取下标 | Unicode 码点区间 `[lo,hi]`，区间随 `rem` 收窄 | 同主方案 |
| 皮 | 浅纸「档案」：米白纸 + 墨字 + 朱红前沿 | 深色「频谱」：深底 + 三色分区噪声 | 同主方案 |
| 噪声观感 | 单色（暖灰）三级由浅到深，安静、像扫描件 | 三色分区（片假名青 / 希腊紫 / 拉丁琥珀），信息量大、像信号分析仪 | 同主方案，另加红色扫描带 |
| 额外元素 | 无 | 页眉实时显示当前档位 `BAND 拉丁 LATIN` | 3 Hz 方块光标（盖住正在解码的那一格）+ 跟随前沿的柔光带 |
| 实现成本 | 低：池是常量，加一档只加一个字符串 | 中：要管码点区间、收窄系数、`String.fromCharCode`；日文/希腊字形宽度不一，观感更"技术"但也更吵 | 低：在主方案上多 ~15 行（一个 div + 三行 `reelDraw`） |
| 可读性 | **最好**：单色噪声 + 朱红暖带，真字一出来对比最强 | 一般：多色噪声抢眼，真字（白）与拉丁档（琥珀）在远处不易区分 | 好，但扫描带在某些帧上会把正在解码的字压暗一点；方块光标每 1/3s 亮/灭一次，抽帧频率一旦与它同频就看不到闪（见踩坑 6） |
| 复用性 | 高：换标题只改 `TITLE` 一个字面量，`STEP` 自动反解 | 高：换语言要换 `BANDS` 的区间表 | 中：光标/扫描带的位置依赖 `geo.slot`，换字号要重算 |
| 帧数/CPU | 16 格 × 150 帧，全部是 DOM 文本 + transform，导出 23s | 同上（多了 `fromCharCode`，可忽略） | 同上 + 2 个额外元素，导出 24s |

**推荐主方案。** 理由：
1. 它的噪声是单色的，「乱码 → 真字」的对比只靠**明度**（暖灰 → 墨）而不靠色相，
   在缩略图/小屏/contact sheet 上都能一眼看出前沿在哪；variant-a 的三色噪声在 384px 宽的
   缩略格里会糊成一片彩色麻点，反而看不出解码进度。
2. 三级收敛用字符池表达最直接，池的每一档可以按目标语言定制（中文标题的最后一档用汉字
   假字，英文标题可以换成大写字母），而 variant-a 的码点区间换语言就得重排区间表。
3. variant-b 的扫描带是「内容驱动」而不是装饰扫光（它的位置就是 `front × slot`，不是
   独立动画），确实提升了「前沿在哪」的可读性；但它引入了两个额外风险：一是柔光带在某些
   帧上会把正在解码的字压暗一点，二是方块光标的高频闪烁与抽帧频率同频时会「隐身」
   （踩坑 6）。所以把它降级为备选，把「前沿」交给下划线填充本身 —— SKILL 也提示过：
   竖线扫光容易被看成分割线。
