# 特效 01 · 粒子聚合（particle morph）

> ⚠️ **本目录已于 2026-09-24 精简**：`variants/`、`qa/`、`probe/`、`evidence/`、`table/` 已按使用者决定删除，
> 现只保留 `index.html` + `README.md`；成片与过程产物不入库，需要时用 `capture.mjs` 从 `index.html` 重导。
> **下文提到的备选实现、取证帧与复现命令已不在磁盘上**，但**结论与实测数字仍然有效**
> （它们本来就是为了支撑这些结论才做的）。本库入口见 [`../INDEX.md`](../INDEX.md)。


> 1200 颗粒子从画面外的散点沿各自的弧线飞入，聚合成「REEL」字形，静止半秒，
> 再径向爆散，露出底下的实心字标。全程**没有任何跨帧状态**：`reelDraw(t)` 是
> `t` 的纯函数，同一个 `t` 截两次逐字节一致。

- 时长 5.0s / 30fps / 1280×720 / 无音轨 / 无字幕 / 无进度条（纯特效）
- 主方案 `index.html` → `out.mp4`
- 备选 `variants/variant-a.html`（DOM 粒子 + CSS 辉光）、`variants/variant-b.html`（点云 + 星座连线）

## 1. 时间轴（三个方案共用，便于横向对比）

| 区间 | 画面 |
|---|---|
| 0.00 – 0.40 | 完整静态壳：标题 + 空舞台（`t=0` 不是高潮） |
| 0.40 – 2.95 | 粒子飞入聚合。每颗粒子自己的窗口 `d0 ∈ [0.40, 1.65]`，时长 `0.80–1.30s` |
| 2.95 – 3.50 | 成形静止 + 一记阻尼余振（`ringScale`，见 §4） |
| 3.50 – 4.62 | 径向爆散（每颗粒子 `e0 ∈ [3.50, 3.80]`，时长 `0.58–0.82s`） |
| 3.88 – 4.55 | 实心字标 `REEL` 在粒子底下淡入 |
| 4.65 – 5.00 | 结束态：字标全亮 + 稀疏碎屑，**不是回到第 0 帧** |

`T_END = 4.65` 是**效果真正结束的时刻**（最后一颗粒子到位 `4.62` ∪ 字标全亮 `4.55` 取大者），
底部 HUD 的进度分母用它而不是 `REEL.duration` —— 原因见 §4.5 和 §6 第 8 条。
`t ≥ T_END` 时进度条满格、百分比 `100`、文案「完成」，三者同源，末帧不会再出现 99%。

## 2. 常见写法为什么在本 skill 里会坏

| 常见写法 | 为什么坏 | 本片怎么改 |
|---|---|---|
| `rAF` + 墙钟 `dt`，粒子 `p += v*dt` | 位置是历史累加的结果。先截 `t=3` 再截 `t=1` 与反过来得到不同画面 | 位置写成闭式解：二次贝塞尔 + `span(t, d0(i), d1(i))`，只喂 `t` |
| 拖尾用「半透明矩形盖住上一帧」 | 直接读上一帧画布 → 跨帧状态。两条轨迹互相污染，seek 顺序一变结果就变 | 每帧画「`t−k·DT` 的解析位置」之间的**线段**（§4.2） |
| `Math.random()` 出起点 / 延迟 / 弧线 | 每次加载都不一样，两次截帧必崩 | `hash(i)` 纯函数；换通道就换常数 `hash(i*3+1)` |
| `animation: fly 2s infinite` | `infinite` 是禁项；且相位由墙钟决定，seek 不可控 | 一条 CSS animation 都不用，全走 `reelDraw(t)` |
| `transition: transform .3s` 当主时间轴 | 浏览器动画时间轴 ≠ 片子的 `t`，没法精确 seek | 每帧直接算值、写一次 |
| `setInterval` 推进 DOM 粒子 | 墙钟 + 掉帧会漂移，seek 到同一 `t` 回不去 | 同上，`reelDraw(t)` 里一次算完 |
| 亮度/大小用「上一帧亮度 × 衰减」 | 又是跨帧状态 | 速度用 `p(t) − p(t−0.033)` **有限差分**，纯解析（§4.4） |

一句话：**粒子系统的每一帧都必须是「`t` 的函数」，不能是「上一帧的函数」。**

## 3. 目标点集怎么来的

`fillText` 画在**离屏 canvas** 上，再按步长扫 `getImageData()` 的非透明像素。
字体、字号、坐标全固定 ⇒ 点集确定，采样是确定性的。

```js
var OW = 1000, OH = 340;
var FONT = '700 250px "Noto Sans CJK SC", "Noto Sans CJK JP", sans-serif';
octx.font = FONT; octx.textAlign = 'center'; octx.textBaseline = 'alphabetic';
var m = octx.measureText('REEL');
var baseY = (OH - (m.actualBoundingBoxAscent + m.actualBoundingBoxDescent)) / 2
          + m.actualBoundingBoxAscent;          // 按「墨迹盒」垂直居中，不是按 em 盒
octx.fillText('REEL', OW / 2, baseY);

var d = octx.getImageData(0, 0, OW, OH).data, xs = [], ys = [];
for (var y = 0; y < OH; y += 3)
  for (var x = 0; x < OW; x += 3)
    if (d[(y * OW + x) * 4 + 3] > 140) { xs.push(x); ys.push(y); }

// 确定性 Fisher-Yates：按行扫描的点序有斜条纹，打散后才像自然散布
for (var j = xs.length - 1; j > 0; j--) {
  var r = Math.floor(hash(j * 1.7 + 0.31) * (j + 1));
  var t1 = xs[j]; xs[j] = xs[r]; xs[r] = t1;
  var t2 = ys[j]; ys[j] = ys[r]; ys[r] = t2;
}
```

### 采样密度 ↔ 粒子数（实测，headless Chromium 量的）

| 量 | 值 |
|---|---|
| 离屏盒子 | 1000 × 340 = 340 000 px |
| `'REEL'` @ `700 250px` 墨迹宽 | 622.5 px |
| 墨迹高（`actualBoundingBoxAscent`） | 185 px（全大写，descent = 0） |
| 阈值 `alpha > 140` 的墨迹像素 | 53 786 px（占盒子 **15.82%**） |
| 步长 3 的候选点 | **5 893** |
| 主方案实际取用 | **1 200**（候选的 20.4%） |
| 主方案平均点距 | √(53786/1200) ≈ **6.7 px** |
| variant-a（460 节点）平均点距 | ≈ 10.8 px |
| variant-b（340 节点）平均点距 | ≈ 12.6 px |

结论：**步长 3 决定候选池，`N` 决定密度。** 1200 颗在 6.7px 点距下字形清晰可读；
降到 340 就必须靠连线（variant-b）或更多节点（variant-a）补信息，否则字形开始散架。
这也解释了为什么 variant-a 一开始用 320 节点时字是糊的，提到 460 才立得住。

## 4. 关键技术点

### 4.1 两段同一套贝塞尔，同一帧只写一次

聚合与爆散是**同一段代码的两个分支**，位置只算一次、只写一次；
两段的衔接天然连续（`t = T_HOLD` 时聚合分支的 `u = 1`，位置正好是 `TARGET`）。

```js
function pos(i, t) {
  var u, x0, y0, cx, cy, x1, y1;
  if (t <= T_HOLD) {                       // ① 飞入
    u = easeOut(span(t, D0[i], D1[i]));
    x0 = SX[i];  y0 = SY[i];  cx = CXc[i]; cy = CYc[i]; x1 = TX[i]; y1 = TY[i];
  } else {                                 // ② 爆散：同一套公式，换三个控制点
    u = easeOut(span(t, E0[i], E1[i]));
    x0 = TX[i];  y0 = TY[i];  cx = FX[i];  cy = FY[i];  x1 = EX[i]; y1 = EY[i];
  }
  var w = 1 - u;
  return { x: w * w * x0 + 2 * w * u * cx + u * u * x1,
           y: w * w * y0 + 2 * w * u * cy + u * u * y1 };
}
```

`START/CTRL/END` 全部来自 `hash(i)`：起点是半径 `780–1160` 的环（几何上保证在画面外），
控制点是中点 + 垂线偏移（决定弧线往哪边兜），终点是从形状中心向外的径向爆散。

### 4.2 拖尾为什么不能用覆盖式 + 解析式拖尾

覆盖式（`ctx.fillStyle='rgba(0,0,0,.15)'; ctx.fillRect(...)` 盖在上一帧上）有两个死穴：

1. 它**读上一帧的画布**。确定性检查会先截 `t=0` 再截 `t=2.5`，而真实播放是正序 ——
   两次的「历史」不同，画出来就不一样。这是本特效最容易翻车的地方。
2. 拖尾长度会随帧率/掉帧变化，`--jobs 2` 下每个 worker 的帧序列还被切开了。

改成**解析式历史位置**：不存状态，而是在 `t − k·DT` 这个**解析时刻**上重新求一遍位置。
`t` 给定了，这 5 个采样点就全给定了，与「之前画过什么」无关。而拖尾画的是
**相邻两个采样点之间的线段** —— 于是「静止 ⇒ 线段长度为 0 ⇒ 自动不画」是免费得到的，
不需要任何额外的速度门限。

```js
var K = 4, DT = 0.042;                       // 拖尾覆盖最近 0.168s
function evalAt(t) {
  for (var k = 0; k <= K; k++) {
    var tt = t - k * DT;                     // ← 解析式的"历史时刻"，不是历史状态
    var off = k * N;
    for (var i = 0; i < N; i++) { /* pos(i, tt) → PX[off+i], PY[off+i] */ }
  }
}
// 画：从最老的一段往最新的一段描，每段一次 stroke
for (var k = K; k >= 1; k--) {
  var o1 = k * N, o0 = (k - 1) * N;
  ctx.globalAlpha = TRAIL_A[k];              // 0.30 / 0.155 / 0.072 / 0.030
  ctx.lineWidth   = TRAIL_W[k];              // 1.9 / 1.5 / 1.1 / 0.8
  ctx.beginPath();
  for (var i = 0; i < N; i++) {
    ctx.moveTo(PX[o1 + i], PY[o1 + i]);
    ctx.lineTo(PX[o0 + i], PY[o0 + i]);
  }
  ctx.stroke();
}
```

`PX/PY` 是**每帧全量重写**的 `Float32Array` 暂存区（`(K+1)×N`），不是跨帧状态 ——
它的内容完全由这一次调用的 `t` 决定。

### 4.3 合批：不是 1200 次 `fill()`，是 11 次

逐粒子换 `fillStyle` 会退化成 1200 次状态切换。这里按「拖尾层 → 速度档」分组，
一层一次 `beginPath()` / `fill()`，一帧只有 **11 次绘制调用**：

```js
for (var k = K; k >= 1; k--) { /* 4 条拖尾 stroke */ }
ctx.beginPath(); for (...) { /* 全体辉光晕：1 次 fill */ } ctx.fill();
for (var b = 0; b < 5; b++)  { /* 5 个速度档：5 次 fill */ }
```

### 4.4 亮度/颜色随速度变化（有限差分，不是衰减器）

```js
var vx = PX[i] - PX[N + i], vy = PY[i] - PY[N + i];   // P[N+i] 就是 t-DT 的解析位置
var sp = Math.sqrt(vx * vx + vy * vy) / DT;           // px/s
BUCKET[i] = Math.min(4, (sp / 420) | 0);              // 0/420/840/1260/1680 → 5 档
```

色带 `#5ce4d6 → #8fe79c → #f6e36b → #ffb04a → #ff7b45`：
静止的成形字是青绿，飞入/爆散的粒子是橙红。**颜色本身就是速度表**，
不需要另画一条图例。半径也随档位 1.62 → 2.85 px。

### 4.5 单一真值来源（含「分母不能用 `duration`」这个坑）

底部那一行的「阶段文字 / 进度条 / 百分比」全部来自**同一次** `reelDraw(t)` 里算出的
**同一个** `prog`，不存在「CSS 动条 + JS 动数字」两条时间线。

这里有个反直觉的点：**分母不能用 `REEL.duration`**。末帧是第 149 帧，`t = 149/30 = 4.9667`，
而 `duration = 5.0`，于是 `t / duration` 永远差 0.033s ⇒ 末帧读到 **99%**，
可文案已经写着「完成」——「文案说完成、数字说没完成」，
正是「100% 配 LOADING」那条规则的**反向版本**，一样刺眼。

改法：分母取**效果真正结束的时刻** `T_END = 4.65`（爆散终止 + 字标全亮），
并把阶段边界也一律改由 `prog` 派生，让「满格」与「完成」在数学上**不可能**分开：

```js
var T_END = 4.65;                                  // 字面量：效果真正的结束时刻
var P_GO = T_GO / T_END, P_HOLD = T_HOLD / T_END, P_BURST = T_BURST / T_END;

function drawUI(t) {
  var prog = clamp(t / T_END, 0, 1);               // 唯一真值来源
  var pi = prog >= 1 ? 4 : prog >= P_BURST ? 3 : prog >= P_HOLD ? 2 : prog >= P_GO ? 1 : 0;
  var pct = pi === 4 ? 100 : Math.round(prog * 100);
  dotEl.style.color = PH_COL[pi];
  phEl.textContent  = PH[pi];            // 待机/聚合中/成形/爆散/完成
  enEl.textContent  = PH_EN[pi];
  fillEl.style.width = (prog * 100).toFixed(3) + '%';
  pctEl.textContent  = pct + '%';
}
```

`t = 4.9667` 时 `prog` 被 `clamp` 到 1 ⇒ 进度条 100%、百分比 100、文案「完成」，
三者同时到位。三个 HTML 用的是**同一段逻辑**。

> **这个底栏是「场景内的 HUD」，不是全片进度条。**
> 它画的是本特效自己的 5 秒，分母是 `T_END`。以后若把多个特效 `concat` 成整片，
> 必须改用 kit 的 `gbar.json` + `REEL.offset`（填充 `(offset + t) / total`），
> 并且**删掉这个自绘底栏** —— 否则它会和 kit 注入的 `.reel-gbar` 同时出现在画面底部，
> 两条进度条打架；而且本特效的 `t / T_END` 在整片时间轴上没有任何意义。

### 4.6 成形后的一记阻尼余振

SPEC 要求 `t≈3.0` 完全聚合、静止 0.5s。但**真的完全静止**会让 contact sheet 里
`t=3.00` 和 `t=3.33` 两格逐字节相同，看上去像死图。这里叠了一个解析的阻尼振铃 ——
所有粒子位置绕形状中心按同一个 `ringScale(t)` 缩放：

```js
function ringScale(t) {
  if (t <= T_HOLD) return 1;                       // 飞行段绝不动，否则会扭曲轨迹
  var d = t - T_HOLD;
  if (d >= 0.5) return 1;
  return 1 + 0.05 * Math.exp(-d * 9) * Math.sin(d * 21);
}
```

对 `p(t)` 与 `p(t−k·DT)` **同时**施加，所以拖尾仍然自洽（余振期间会出现一层很短的
径向虚影，正好是「被敲了一下的金属字形」的观感）。它同样只依赖 `t`，不破坏确定性。

## 5. 方案对比

三份 HTML 的**时间轴、配色、目标点集、结束态完全一致**，只有「怎么把点画出来」不同。
导出条件相同：`--jobs 2`，8 核 / 3.6GB 内存 / `--disable-gpu`（纯软件光栅）。
下表是**修完 HUD 读数后重新导出的最终一轮**实测值（机器是共享的，绝对值会随负载浮动，
但三者之间的比例关系稳定）。

| | 主方案 `index.html` | `variant-a` | `variant-b` |
|---|---|---|---|
| 载体 | Canvas 2D | 460 个 `<i>` + 父层 `filter` | Canvas 2D |
| 节点/粒子数 | **1200** | 460 | 340 |
| 拖尾 | 4 段解析线段 | 元素自身拉伸（`rotate` + `scaleX`），沿速度方向 | 3 段解析线段 |
| 辉光 | 加色（`lighter`）+ 一层大半径晕 | `drop-shadow()` ×2（CSS 滤镜） | 加色 + 一层大半径晕 |
| 额外信息层 | 速度→颜色分档、径向爆散闪光 | 同上（`currentColor` 换色） | **距离 < 30px 的点之间连线** |
| 一帧绘制调用 | 11 次（4 stroke + 1 晕 + 5 档 + 1 底） | 460 × 3 次样式写入 + 1 次整层滤镜 | 11 次 + 1 次连线 stroke |
| 实测导出耗时 | **1m31.3s** | **8m52.4s** | **1m46.8s** |
| `real / user` | 1m31 / 2m57 | 8m52 / 3m13 | 1m47 / 2m59 |
| `out.mp4` 体积 | 6.40 MB | 2.25 MB | 2.56 MB |
| 可读性 | 最好，字形饱满 | 尚可（点距 10.8px，靠发光晕补） | 好，但字被弦线「切角」，更像网 |
| 确定性 | ✅ 逐字节一致 | ✅ 逐字节一致 | ✅ 逐字节一致 |
| 复用性 | 高（改字/改图只换离屏采样） | 中（要重建 460 个节点） | 高（加一个 `LINK_R` 参数） |

### 推荐：主方案 `index.html`

理由是**代价曲线不对称**：

- variant-a 的 `real 8m52s` 里 `user` 只有 `3m13s` —— 它**不是被 CPU 卡住的，是被等**。
  `filter: drop-shadow()` 加在一个 1280×720、内含 460 个每帧都在动的子节点的层上，
  等于每帧都要把整层离屏光栅化、再做两遍模糊；CDP 截图必须等这条流水线走完。
  也就是说：**只要还想加节点或加滤镜，成本会继续非线性上涨**（460 节点是主方案导出时间的
  5.8 倍，而节点数只有主方案的 38%）。它的发光质感确实更「软」，
  但代价是分辨率、节点数和迭代速度全都要让步。
- variant-b 的 `1m47s` 只比主方案贵 17%，换来「图结构」这一层信息。它的观感很有辨识度
  （能看出字形，也能看出网络），但弦线会横跨字腔（比如 `R` 的碗和腿之间），
  字形边缘比主方案毛。它适合「数据/网络」语境，不适合要把字形当主视觉的时候。
- 主方案 1m31s 拿到 1200 颗粒子、6.7px 点距、干净的拖尾和最饱满的字形，
  **在这个题材上性价比压倒性**。

如果一定要在「发光质感」上加码，正确的做法不是给 DOM 加滤镜，而是在主方案的
Canvas 上再加一层半径更大的加色晕（`fillStyle` 一次、`globalAlpha` 调低），
成本几乎是零 —— 主方案里的辉光晕就是这么做的。

## 6. 踩坑记录

1. **variant-a 成形后是白的，不是青的。**
   元素背景原本写的是 `linear-gradient(90deg, transparent 0%, currentColor 72%, #fff 100%)`。
   静止时 `scaleX = 0.08`，元素只有最右侧 8% 露出来 —— 正好是那段 `#fff` 的高光头。
   于是「按速度上色」在静止帧完全失效，字形是一团发白的糊点。
   改成 `currentColor` 一直铺到 100%、去掉白头后，静止帧才正确显示档位 0 的青绿色。

2. **variant-a 导出 7m20s，`user` 只有 2m47s。**
   一开始以为是自己粒子写太多，但 `real ≫ user` 说明进程在等，不在算。
   根因是父层 `filter`：它把 1280×720 的整棵子树每帧重新离屏光栅化并做两遍模糊。
   这也是「DOM 方案能省 CPU」这个直觉在本机不成立的原因 —— 省的是 JS，花的是合成器。

3. **contact sheet 第 10、11 格逐字节相同。**
   SPEC 要求 `t≈3.0` 静止 0.5s，真静止就让 `t=3.00` 和 `t=3.33` 两帧完全一样，
   看上去像画面卡死。加了 §4.6 的 `ringScale` 阻尼余振后两格才区分开，
   而且它仍然是 `t` 的纯函数（当时的机器验收 的确定性检查依旧通过）。

4. **DOM 字标和粒子形状对不齐。**
   canvas 采样是按 `actualBoundingBoxAscent/Descent`（墨迹盒）垂直居中的，而 DOM 的行盒
   是按字体 `ascent/descent` 摆基线的，两者差 `(A−D)/2 − (aI−dI)/2`。实测
   `aI=185, dI=0, A=290, D=72` ⇒ 差了 **16.5px**。用同一个字体在离屏 canvas 上量出这四个
   数再给字标加 `translateY`，两个方案的字才落在同一基线上。
   （主方案不需要这一步：字标和采样用的是同一个 `fillText`、同一个 `baseY`，天然对齐。）

5. **`infinite` / `transition` 这两个词连注释都不能写。**
   当时的机器验收 是在**整个 HTML 文本**上跑正则的（`/\binfinite\b/`、`/\btransition\s*:/`），
   注释里出现也会被判违规。本文件的「禁用项」段落因此只用中文描述，不写英文词。

6. **`--jobs 8` 会 OOM。** 本机 3.6GB 内存、`--disable-gpu`，每个 worker 是一个完整
   Chromium + 一个 1280×720 的离屏层。全部导出都用 `--jobs 2` 串行跑，一次一个 capture。

7. **节点数不是「先随便定」**：variant-a 第一版 320 个节点，字形是糊的
   （点距 12.9px，而元素本体只是一条 2.6px 的短划）。提到 460（点距 10.8px）才立得住。
   这个数是从 §3 的采样密度表反推的，不是试出来的。

8. **末帧「文案说完成、数字说 99%」—— 复核退回一轮才修掉。**
   进度原本写成 `t / REEL.duration`。`duration = 5.0`，而最后一帧是第 149 帧、
   `t = 149/30 = 4.9667`，**永远差 0.033s**：末帧放大看就是左边「完成 COMPLETE.」、
   右边 **99%**、进度条还差一小截。这不是"差 1% 无所谓"——它是
   SKILL.md 硬规则「数值到终点文案已是结束态（不要 100% 配 LOADING）」的**反向违反**：
   状态说结束了，数字说没结束。
   根因是**分母选错了对象**：`duration` 是"片长"，不是"效果结束时刻"。
   改成 `T_END = 4.65`（爆散终止 + 字标全亮），并把阶段判定也改由 `prog` 派生（§4.5）。
   教训：**只要画面上同时有"状态文案"和"进度数字"，它们必须由同一个归一化量派生，
   而那个量的分母要是"事情做完的时刻"，不是"容器有多长"。**
