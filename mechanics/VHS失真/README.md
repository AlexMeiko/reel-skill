## 1. 核心命题：逐扫描线的位移是**闭式**的

整个特效只有**一条**真正的运动来源：每条扫描线的水平位移 `dx(y, t)`。它被写成三项之和，
每一项都只依赖 `(y, t)` —— **没有任何 `dx += …`，没有"上一帧"，没有跨帧状态**。

```js
q(t)    = floor(18 * t)                          // 时间量子：18Hz（≠30fps，不退化成逐帧噪声）
ramp(t) = span(t, 0.18, 0.55)                    // 起手斜坡：t=0 时振幅为 0 → 完整静态壳
bp(t)   = ((240 * t) % 780) - 60                 // 磁头噪声带顶边（取模相位，不累加）

J(y,t)  = 2.4 * ramp(t) * (2*hash(1.0*y + 13.7*q) - 1)
H(y,t)  = [ bp <= y < bp+16 ] * 30 * (2*hash(2.3*y + 5.1*q) - 1)
K(y,t)  = Σ_i  E_i(t) * [ 12*(2*hash(4.7*y + 9.1*i + 2.3*q) - 1)
                        + 46 * d_i * 1{ y ∈ z_i } ]

dx(y,t) = J(y,t) + H(y,t) + K(y,t)               // ★ 三项相加，一次算完
```

### 三项各自的视觉职责（不是三个"差不多"的抖动）

| 项 | 时间行为 | 空间行为 | 视觉职责 |
|---|---|---|---|
| **J** 基础抖动 | 每 1/18 s 整幅换一次相位 | 逐行独立、幅度小（±2.4px） | 让画面"毛"起来。它是 VHS 的底色噪声，也是「这不是数码图」的第一眼信号。因为逐行独立，画面不会整块平移，而是像被细齿梳过 |
| **H** 磁头噪声带 | 位置按 `bp(t)` 以 240px/s **持续向下滚动**，永不停止 | 只在 16px 高的一条带内，带内逐行 ±30px | 磁头切换瞬间的失同步。它是「本片一直在动」的持续证据，也是失真的节奏底噪 |
| **K** 偶发跳变 | 只在字面量节拍表上的六个时刻发作（含两对密集双发） | 全幅逐行踢 ±12px **加上**一条撕裂带整条同向跳 ±46px | 真正的「磁迹丢失」事件：画面被横向撕开、短暂失去同步。它和 J 的区别就是「常在的细抖」vs「有节奏的爆发」 |

### 为什么"三项相加"是重点，而不是把三层效果叠起来

因为**三项必须共享同一个 y 坐标系**：撕裂带 `z_i` 是一个行区间，噪声带 `H` 是一个行窗口，
基础抖动 `J` 是逐行相位。如果按「先整体抖一层、再叠一条噪声带、再叠一次撕裂」分层做，
分层之间就会出现**各自独立的行坐标**（层被 translate 之后行号就不同了），
撕裂带会跟着它所在的那一层漂移 —— 观众看到的是"三条互不相干的动画"，不是"一条信号被三种机制同时干扰"。
一次算完再写一次，还顺带满足了 同一元素同一帧只写一次「同一元素同一帧只写一次」。

主方案里这一段（`index.html`，逐行合成循环）：

```js
for (var y = 0; y < H; y++) {
  /* ★ 闭式三项相加，一次算完，没有任何累加器 */
  var dx = termJ(y, q, ramp) + termH(y, bp, q) + termK(y, q, E);

  var s   = clamp(dx / DXMAX, -1, 1);
  var sep = CA0 + cag * s;                 // ★ 有符号色散，方向跟着 dx 走
  drawWrapped(CHR, y, dx + sep);
  drawWrapped(CHG, y, dx);
  drawWrapped(CHB, y, dx - sep);
}

/* 逐行画一条扫描线，并对画布外的那一段做水平环绕 */
function drawWrapped(src, y, d) {
  vctx.drawImage(src, 0, y, W, 1, d, y, W, 1);
  var k;
  if (d > 0.5)      { k = Math.ceil(d);  vctx.drawImage(src, W - k, y, k, 1, 0, y, k, 1); }
  else if (d < -0.5){ k = Math.ceil(-d); vctx.drawImage(src, 0, y, k, 1, W - k, y, k, 1); }
}
```

> **三个通道都必须环绕**（这一点是被实测逼出来的，见 §8.3）：
> 只环绕 G 的话，被位移"拽出去"的那一侧会整段丢掉 R 和 B，
> 在最强一次失同步里右边缘有 **67/720 行只剩 G**，渲成一条 ~40px 宽的纯绿竖条 ——
> 读起来像渲染错误，而不是磁带瑕疵。
> 环绕之后边缘不再缺通道，**色散仍然完整存在**：它体现在 R / G / B 三张平面
> 彼此错开 1–16px，所以画面内部的字形边缘、地平线、山脊上都能看到红/青描边。

## 2. 色散：三个通道各自独立位移，且**方向必须与 dx 同号**

主方案里 R / G / B 不是"半透明叠加"，而是把源帧真的拆成三张单通道平面
（`drawImage` + `globalCompositeOperation = "multiply"` 填纯红/绿/蓝），
再用 `globalCompositeOperation = "lighter"`（等价 `mix-blend-mode: screen`，加色）逐行合成。
三张平面各自有**自己的行位移**：

```
sep(y,t) = CA0 + (CAG0 + CAG1 * syncEnv(t)) * s(y,t)      // ★ 有符号量
           CA0=1.7  CAG0=5.5  CAG1=9.0   DXMAX=34
           s = clamp(dx / DXMAX, -1, 1)
dxR = dx + sep        dxG = dx        dxB = dx - sep
```

### 为什么 `sep` 必须带 `dx` 的符号（否则看着"贴上去"）

`sep` 是一个**有符号**量：`s` 取 `dx` 的归一化符号。于是

* `dx > 0`（这一行被推到右边）→ `sep > 0` → **R 推得比亮度更右，B 更左**；
* `dx < 0`（这一行被推到左边）→ `sep < 0` → **R 推得更左，B 更右**。

也就是说：**线条往哪边跑，色散就往哪边拉**。观众读到的是"这一行连同它的颜色一起被拽走了"，
是**分离**。

如果反过来，用一个恒正的 `sep`（R 永远在右、B 永远在左），不管线条往哪跑、
不管失同步有多猛，红边永远固定在同一侧 —— 眼睛立刻会把它读成**一层彩色膜贴在画面上面**，
因为它和画面上发生的事没有任何因果关系。这跟 动效不炫技
（"扫光/高光必须承载信息"）是同一个道理：**装饰和效果的差别，就是它跟不跟着主变量走。**

`CA0 = 1.7px` 是 `dx = 0` 时仍然存在的静态色差 —— 这正是 SPEC 要求的
「`t=0` 画面已在位（略带色差）」：`t=0` 时 `J=H=K=0`，但 R / B 已经各偏 1.7px。

**这一条正是 variant-a 做不到的地方**：`feTurbulence` 是零均值噪声场，位移方向不可控，
色差只能做成固定方向。`variants/compare-t276.png` 里三张并排图可以直接看到差别 ——
variant-a 的字形周围是一圈**恒定方向**的红/青膜。这不是实现偷懒，是这一路方法的**固有上限**。

## 3. 「随机感」怎么造：`hash` + 时间量子，以及 `Math.random()` 会坏在哪

```js
function hash(i) {                    // 确定性伪随机：同一 i 永远同一结果
  var x = Math.sin(i * 127.1 + 311.7) * 43758.5453123;
  return x - Math.floor(x);
}
var q = Math.floor(t * 18);           // 时间量子：每秒换 18 次
```

* **`hash(i)` 负责"每条线不一样"**：`hash(1.0*y + 13.7*q)` 把 720 行映射到 720 个互不相干的相位，
  所以画面是"逐行被梳"而不是"整块平移"。
* **`q = floor(18t)` 负责"每一刻不一样"**：量子把连续时间切成 1/18 s 的格子。
  18Hz 是刻意的 —— **不能取 30/60Hz**（与帧率同频 → 退化成逐帧噪声，看不出节拍），
  取 18Hz 时一个量子跨 1.67 帧，掉帧不变样，人眼能数出"咔咔咔"的换相感。
* 需要多条独立随机通道就换常数：`hash(y*4.7 + 9.1*i + 2.3*q)`（K 项）、`hash(y*2.3 + 5.1*q)`（H 项）。

### 换成 `Math.random()` 会坏成什么样

1. **同一 `t` 截两次不一样** —— 当时的机器验收 的第一条确定性检查直接 FAIL。
   这不是"擦边"，因为 `capture.mjs` 会为了抽帧、确定性复核、contact sheet 多次 seek 同一个 `t`。
2. **导出的 150 帧永远不可重现** —— 改一句别的东西重导，画出的是另一盘磁带，README 里的抽帧全部作废。
3. **一个更隐蔽的坏法**：如果为了"看起来随机"把 `Math.random()` 用在**离散量**上
   （比如"这一行要不要撕裂"），那么同一帧内不同行、以及相邻帧之间，
   撕裂带的位置会**逐次重掷**。视觉上它不再是"带子"，而是"一片闪烁的噪点"——
   因为真实的撕裂是**空间连续**的（一整段行一起跳），而独立重掷破坏了这个连续性。
   K 项里 `1{y ∈ z_i}` 是一个**区间**判断，就是在保住这个连续性。

顺带一提，「随机感」在 VHS 里其实主要来自**量子化的相位切换**，不是来自均匀随机数。
18Hz 量子 + 逐行 hash 已经足够"乱"，而且它可复现。

## 4. 常见写法为什么在本 skill 里会坏（逐条点名）

| 常见写法 | 坏在哪 | seekable 改法 |
|---|---|---|
| `animation: roll 2s infinite`（噪声带滚动） | `infinite` 被 lint 直接判 FAIL；而且 CSS 动画的 `currentTime` 在 seek 后要等补间跑完，画面滞后于 `t` | `bp = ((t*240) % 780) - 60` —— **取模相位**，闭式、无累加、可任意 seek |
| `bandPos += 8`（每帧推进） | 纯累加器：当时的机器验收 的「换 seek 路径」检查会抓住它（直接 seek 到 2.5 和先经过 0/1.25 再到 2.5 会得到不同画面）。它甚至能通过"同 t 两次一致"，因为每次都按同一顺序 seek（见 PATTERNS §8） | 同上：位置写成 `t` 的函数，不要写成"上一帧位置 + 增量" |
| `noise[i] = Math.random()` | 同一 `t` 两次截帧不一致 → FAIL；且画面不可复现 | `hash(i)`；需要多通道就换常数 `hash(i*3+1)`、`hash(i*7.7+13.3)` |
| 墙钟 `requestAnimationFrame` | lint 要求 rAF 只能读 `window.__reelTime`；墙钟 rAF 的画面与 `t` 无关，当时的机器验收 的换路径检查会露馅 | 全部走 `reelDraw(t)`；本特效连 rAF 都不需要 |
| `transition: transform .2s`（抖动过渡） | `transition` 是墙钟补间，seek 不会等它跑完 → 画面停在过渡中间态；lint 对视觉属性的 `transition` 直接 FAIL | 每帧在 `reelDraw` 里算出**唯一最终值**再写一次 |
| 每帧改 DOM 文本（时间码） | Chromium 字形缓存的栅格化路径会随合成层时机变化，同 `t` 两次截帧差 1/255（PATTERNS §6.1，只在系统高负载时复现） | 把时间码画进 `<canvas>` 的 `fillText`。主方案整幅画面（含所有文字）都在一张 canvas 上，DOM 里一个文本节点都没有 |
| 用 `<video>` / 外链字体 / `<script src>` | lint 直接 FAIL（本 skill 要求自包含单文件） | 场景全部程序化绘制；中文用系统 `Noto Sans CJK SC` |
| 分层 `<div>` 各自 `translate` | 各层有各自的行坐标系，撕裂带会跟着层漂移 →"三条互不相干的动画" | 一次算完 `dx(y,t)`，逐行只写一次 |
| 720 个 1px `<div>` 做逐扫描线 | 能跑，但实测渲染 **~0.50 s/帧**（主方案 canvas 的 5×），且色散要三份克隆就是 2160 个 div | 用 canvas：`drawImage` 逐行（实测 ~0.1–0.6 s/帧，见 §7） |

## 5. 关键技术点

### 5.1 起手是完整静态壳（`t=0` 一定干净）

```js
var ramp = span(t, 0.18, 0.55);        // J 项的振幅包络
```
`t=0` → `ramp=0` → `J=0`；`bp(0) = -60`（噪声带整个在画面上方）→ `H=0`；
`BEATS` 最早一次在 1.26s → `K=0`。于是 `dx ≡ 0`，只剩 R/B 各 ±1.7px 的静态色差。
这是**结构性**保证，不是"刚好第一帧看不出来"。

### 5.2 噪声带的取模相位

```js
var BSPEED = 240, BPERIOD = 780, BOFF = -60;   // 780 = 720 + 60
var bp = ((t * BSPEED) % BPERIOD) + BOFF;
```
* `780 = 720 + 60`：带子完全滑出下边缘（`bp = 720`）之后才回到 `bp = -60`（完全在画面上方）。
  换圈的两个端点都在画面外，所以**换圈不可见**。
* 240px/s 在 30fps 下是 8px/帧 —— 足够慢到看得出方向，足够快到不"粘"。
* 周期 `780/240 = 3.25s`，5s 片长里换 1.0 圈多一点，取模真的被走到（不是"写着好看"）。

四个采样帧的实测位置（`probe/`）：`t=0.0 → bp=-60`（画面上方）、
`t=1.5 → 300`、`t=2.5 → 540`、`t=4.96 → 350`。**位置每次都不同 → 确实在纵向滚动，不是原地闪。**

### 5.3 磁迹丢失：字面量节拍表 + 平台包络

```js
var BEATS = [
  { t: 1.26, w: 0.14, a: 0.72, z: [ 96, 268], d:  1 },
  { t: 1.34, w: 0.12, a: 0.95, z: [380, 520], d: -1 },   // ← 密集双发
  { t: 2.70, w: 0.20, a: 0.85, z: [108, 660], d:  1 },   // ← 全幅失同步（峰值帧见 compare-t276.png）
  { t: 3.85, w: 0.16, a: 0.62, z: [300, 452], d: -1 },
  { t: 4.40, w: 0.14, a: 0.88, z: [ 60, 240], d:  1 },
  { t: 4.46, w: 0.16, a: 1.00, z: [430, 690], d: -1 }    // ← 密集双发 + 最强收尾
];

function envAt(t, b) {                 // 瞬时起振(0.03s≈一帧) → 平台 → 二次衰减
  var d = t - b.t;
  if (d < 0 || d > b.w) return 0;
  var atk = 0.03, hold = b.w * 0.45;
  if (d <= atk)  return b.a * (d / atk);
  if (d <= hold) return b.a;
  var u = (d - hold) / (b.w - hold);
  return b.a * (1 - u) * (1 - u);
}
```

* **间隔刻意不等距**（1.26→2.70→3.85→4.40 是 1.44 / 1.15 / 0.55s，中间嵌两对 ~0.08s 的双发），
  所以看得出节奏，不是节拍器。
* **用平台包络而不是三角尖**：如果直接用三角形，可见时长只有 `w` 的 1/3，播放时一闪而过；
  平台版的"起振到到位"只占 0.03s（一帧内），之后保持 `0.45w` 再二次衰减。
  副作用是好的：撕裂带的开关切换发生在振幅已经足够大的那一帧，看不到干净壳与撕裂之间的拼缝。
* **`z`（撕裂带行区间）和 `d`（整条同向跳的符号）都是字面量**，不靠 hash 掷骰子 ——
  这是"可读性/可复核性"的选择：README 里写的和代码里跑的是同一张表。
* 最后一次发作在 `4.46 + 0.16 = 4.62` 结束，末帧 `4.9667` 处 `syncEnv = 0`，
  撕裂带完全退场 —— 满足"末帧干净、稳定"。

### 5.4 仪表自洽（场景内仪表自洽）

场景内只有两个读数量：右下角的**时间码**和它上面的 **TRACKING OK / LOST**。

* 两者都由**同一个** `t` 派生，没有第二条时间线（不存在"CSS 动条 + JS 动数字"）。
* 末帧到终点值：帧号 `f = min(149, round(t*30))`，`t=4.9667 → f=149 → 00:00:04:29`。
  用 `t/duration` 当分母就会停在 99%（PATTERNS §6.2 的坑），这里用**帧号**，天然到点。
* 全片只有**一张**节拍表（`BEATS`）定义"开始/结束时刻"，状态字也只看它的包络。
* 按 parent 要求**没有手画全片进度条**。因此将来若把这些特效 concat 成整片，
  场景内仪表不会和 kit 的 `gbar.json` 底栏打架；若确实要把时间码/状态接进 kit，
  应改走 `gbar.json` + `REEL.offset`（本片 `REEL` 里没有 `offset`，即未启用）。

## 6. 三方案对比

三个方案用的是**同一条时间轴、同一张节拍表、同一个场景**，只有"怎么把像素挪开"不同。
`variants/compare-t276.png` 是同一个峰值帧（t=2.76，全幅失同步）的并排对比。

| | 主方案 `index.html` | `variant-a` | `variant-b` |
|---|---|---|---|
| 机制 | 720 行 × 每行 3~6 次 `drawImage`（Skia 合成） | 1 个 SVG `<filter>`：`feTurbulence`×3 + `feDisplacementMap`×3 + `feBlend screen`×2 | `getImageData` → `Uint8ClampedArray` 逐像素取样 → `putImageData` |
| 闭式 `dx(y,t)` 三项 | ✅ 逐扫描线，完整 | ❌ **没有**。位移 = 噪声场 × `scale`，只有包络可控 | ✅ 逐扫描线，完整 |
| 逐行结构可控 | ✅ 每一行都能点名 | ⚠️ 由 `baseFrequency` 决定，只能"大概像" | ✅ 每一行都能点名 |
| 色散方向 | ✅ 有符号 `sep`，随 `dx` 换边（**分离**） | ❌ 固定方向（R 恒右、B 恒左）→ **像一层彩膜贴上去** | ✅ 有符号 `sep`，随 `dx` 换边 |
| 边缘 | 三通道全部环绕 | 滤镜区域外溢出被裁 | 三通道全部环绕（取模，天然） |
| 亚像素 | ✅ `imageSmoothing` 插值 | ✅ 滤镜自带插值 | ❌ 量化到 1px（最糙） |
| 峰值帧的破坏力 | 全幅逐行撕开、标题不可读（真·失同步） | 只是"波浪化"，标题仍清晰可读（**打不到峰值**） | 与主方案几乎一致，边缘略更毛糙 |
| 渲染成本（成对实测，见 §7） | 0.10 – 0.57 s/帧 | 0.37 – 0.50 s/帧 | **0.00 – 0.06 s/帧** |
| 整片导出（150 帧，实测） | 233.0 / 272.8 / 342.8 s | **189.6** / 227.2 s | 182.9 / 229.2 s |
| 成片体积 | 9.7 MB | **3.9 MB** | 10.3 MB |
| 代码量 / 可读性 | ~350 行，几何全是命令式 | ~300 行，场景是声明式 SVG，失真就是一段 `<filter>` | ~310 行，主循环是纯索引算术，**最好懂** |
| 复用性 | 高（换 `BG` 就是另一盘带） | 高（换滤镜参数即可，但风格也一起换） | 高 |

### 推荐：**主方案**（`index.html`）

1. 只有它同时满足「逐扫描线闭式 `dx`」+「色散方向随 `dx` 换边」+「亚像素插值」。
   variant-b 满足前两条，但位移量化到 1px，撕裂边缘明显更毛糙；
   variant-a 一条都不满足，而且**在峰值帧根本打不出失同步**（`compare-t276.png` 第 2 格）——
   它是拿来对照的**反例**，不是备选。
2. 渲染比 variant-a 便宜（主方案 0.1–0.6 s/帧 vs variant-a ~0.4 s/帧），
   而 variant-a 唯一的优势（导出更快）来自"画面被滤镜抹平了、PNG 小"，不是来自它更好。
3. **如果只想要最快**：选 variant-b。它渲染最快（~0.05 s/帧）、代码最好懂、同样有闭式 `dx` 与
   有符号色散，代价是 1px 量化。**这是本片最反直觉的结论**（见 §7 最后一段）。
4. **不要选 variant-a**，除非你要的就是"滤镜式的柔和波浪感"而不是"磁带失同步"。

### 与 SPEC 的一处刻意偏差（说明理由）

SPEC 给主方案写的是「DOM 克隆层 + `clip-path` 条带 + `mix-blend-mode: screen`」，
条带数是个位数。但 parent 的硬性要求是**逐扫描线**的闭式 `dx(y,t)` ——
个位数条带只能给出"逐条带"的位移；720 个 `clip-path` div 才是逐扫描线，而那样做：

* 实测（`_bench/domrows.html`：720 个 1px 高的 div，**只做位移、还没叠色散**）
  渲染 **≈0.50 s/帧**，而色散要三份通道克隆 = 2160 个 div。
* 所以主方案把"三份克隆层 + screen 混合"**原样搬到 canvas**：
  `drawImage`+`multiply` 拆通道 ≡ 克隆层，`globalCompositeOperation='lighter'` ≡ `mix-blend-mode: screen`。
  语义完全一致，但拿到了逐扫描线的控制权。

variant-a / variant-b 则严格按 SPEC 实现（SVG 滤镜 / 逐像素）。

## 7. 性能实测（parent 问的「逐扫描线 1080 行会不会很慢」）

### 7.1 方法

* **渲染成本**：同一个页面做两个版本 —— 原版，和"把 `reelDraw` 包一层、只在 `t=0` 真渲染"的
  **静态版**（图像一样、编码成本一样，但不逐帧渲染）。用 `capture.mjs --at` 各打 **10 个采样帧**，
  `(原版 − 静态版) / 10` = 每帧渲染成本。两轮**交替相邻**跑，抵消宿主负载漂移。
* **导出耗时**：`capture.mjs --out … --jobs 1`，150 帧全量。

### 7.2 渲染成本（秒/帧）

| 页面 | 第 1 轮 | 第 2 轮 | 结论 |
|---|---|---|---|
| **主方案 `index.html`** | 0.57 | 0.10 | **0.1 – 0.6**（宿主争用敏感） |
| **`variant-b.html`**（逐像素） | 0.06 | 0.00 | **≤0.1** ← 最快 |
| **`variant-a.html`**（SVG 滤镜） | 0.50 | 0.37 | **≈0.4** ← 最贵 |
| `_bench/domrows.html`（720 个 DOM div，只位移） | 0.50 | — | ≈0.5（且不含色散） |

### 7.3 整片导出耗时（150 帧，1280×720@30fps）

| 方案 | 单跑 | 同一作业连续三轮 | 成片 |
|---|---|---|---|
| 主方案 | 233.0 / 272.8 s | 342.8 s | 9.7 MB |
| `variant-a` | **189.6 s** | 227.2 s | 3.9 MB |
| `variant-b` | 182.9 s | 229.2 s | 10.3 MB |

> 本机同时有多个子代理在导出别的特效（`/proc/loadavg` 在 1.8 – 9.8 之间跳），
> 绝对秒数波动可达 ±50%。**相对关系在两套条件下一致**：variant-a 最快、variant-b 居中、主方案最慢。

### 7.4 结论

* 720 行 canvas 逐扫描线（每行 3–6 次 `drawImage`，共 ~4400–5900 次/帧 + 6 次全画布混合）
  是 **0.1–0.6 s/帧**，150 帧 15–90 s。**可以用 canvas 逐扫描线，不必为了性能降级成"逐条带"。**
* DOM 逐扫描线 ~0.5 s/帧（且不含色散）—— parent 的担心成立。
* **最反直觉的一条**：`variant-b` 的"逐像素 JS 循环"反而是**最快**的渲染器。
  原因是主方案的瓶颈不在像素运算量，而在 **~4400 次 `drawImage` 的调用开销**；
  而 variant-b 是一次 `getImageData` + 一次线性扫描 + 一次 `putImageData`，
  921600 个像素在 typed array 上是纯内存拷贝。
  **"像素级做法最慢"这个直觉在本特效里是错的。**
* **导出总耗时主要由"画面有多噪"决定，不由渲染循环决定**：
  平坦图 PNG ~0.54 s/帧，噪声图 ~1.4 s/帧。variant-a 渲染最贵，却导得最快，
  因为它的画面被滤镜抹平了（成片 3.9 MB vs 主方案 9.7 MB）。
  **要压缩导出时间，先降噪声，不是先优化渲染循环。**

## 8. 踩坑记录

### 8.1 全量导出 8.5 分钟，比预期（1–3 分钟）慢一个量级

第一次全量导出 `MAIN_ELAPSED=511.62 s`。第一反应是"逐行 `drawImage` 太慢"，差点去改算法。
先用基准页把成本拆开（§7），才发现渲染只占小头 —— **推理错了**。
真凶是噪声图的 PNG 编码：平坦图 ~0.54 s/帧、噪声图 ~1.40 s/帧，**差值 ~0.86 s/帧全在编码**；
再加上 x264 编码 10MB 的噪声视频。后来发现同一台机器上还有别的子代理在并发导出，
`loadavg` 一度到 9.8，所以 511.6s 里也混着争用。
教训：**遇到"导出慢"，先把"渲染"和"编码"分开量，别直接改渲染循环。**

### 8.2 `variant-b` 不声明 `willReadFrequently`，每帧 `getImageData` 走一次 GPU→CPU 回读

`getImageData` 在 GPU 后端的 2D canvas 上会强制一次同步读回。
加 `getContext("2d", { willReadFrequently: true })` 之后，variant-b 的渲染成本落进测量噪声（≤0.06 s/帧）。
一行参数的差距，就是"回读同步等待"和"CPU 内存直接读"的差距。

### 8.3 ★ 只环绕 G 通道 → 最强失同步时右边缘一条 40px 纯绿竖条

**症状**：`sheet.png` 第 11 格（t≈3.79）右侧有一道竖直的亮绿色块，像是渲染错误。

**定位**：写了个逐行判据 —— 右边缘 40 列里"G 明显而 R、B 都接近 0"的行数：

```
t=0.00  greenOnlyRows=0/720
t=0.50  greenOnlyRows=0/720
t=1.38  greenOnlyRows=1/720
t=2.76  greenOnlyRows=0/720
t=4.48  greenOnlyRows=67/720     ← 坐实
```

**根因**：第一版只给 G（亮度）做水平环绕，理由是"R/B 的边缘缺口正好就是色散边缘"。
这在 `|dx|` 小的时候成立（缺口 1–4px，就是描边）；但在最强一次失同步里
`dx` 能到 −60，于是 `dR = dx + sep ≈ −73`、`dB = dx − sep ≈ −47` ——
右边缘 **73px 丢掉 R、47px 丢掉 B**，那一段只剩 G，就是一条纯绿竖条。

**修法**：三个通道都环绕（`drawWrapped`）。代价是每行多 2 次 `drawImage`（~4400 → ~5900 次/帧）。
**修复后**：`t=1.38 / 2.76 / 4.48` 全部 `greenOnlyRows=0/720`。
色散并没有因此消失 —— 它本来就该体现在"三张平面彼此错开"上，而不是"边缘缺通道"。

### 8.4 主方案第一版的字体名写错了

写成了 `"Noto Sans Sans CJK SC"`（多一个 Sans）。canvas 的 `font` 解析对无法识别的族名
**静默回退**到默认字体，不报错 —— 中文照样显示（系统有 fallback），但字形跟设计不一致。
这正是 AGENTS.md 说的"优先排查静默失败"。之后所有字体串都收敛到两个常量：

```js
var MONO = '"Noto Sans Mono CJK SC", ui-monospace, monospace';
var SANS = 'system-ui, "Noto Sans CJK SC", sans-serif';
```

### 8.5 `feTurbulence` 只在 filter region 内生成噪声 → 大 `dy` 会把位移图打空

variant-a 要让噪声场滚动，第一版想直接 `feOffset dy = bp`（最大 719）。
但 `feTurbulence` **只在自己那块 filter region 内产生噪声**，`dy=719` 会把 region 顶部
掏出一大片"空"（R=G=0）；`feDisplacementMap` 拿到 0 会算成 `scale*(0-0.5) = -scale/2`，
**那一大片会整块被推到一个固定的大偏移上**，画面直接撕裂成两半。

修法（两层保险）：

```js
var PERIOD_Y = 1 / 0.04;                                  // 噪声在 y 方向的周期 = 25 单位
var ph = ((bp % PERIOD_Y) + PERIOD_Y) % PERIOD_Y;         // 只取"对周期取模"的位移
oR.setAttribute("dy", ph.toFixed(2));
```

`feTurbulence` 的输出对每个 octave 都是**周期函数**（周期 = 1/frequency），
所以"对周期取模的位移"和"无限滚动"是**逐像素等价**的 ——
既不会掏空 region（位移恒 < 25），又拿到了真正的滚动。

### 8.6 整幅画面（含文字）都画进 canvas，DOM 里零文本节点

PATTERNS §6.1 记录过：每帧改 DOM 文本会踩 Chromium 字形缓存的 1/255 抖动，
**只在系统高负载时复现**，空载跑十次全过 —— 属于最难查的一类。
本特效的时间码每帧都在变，所以从第一版就把 HUD 一起画进 canvas（`ctx.fillText`），
主方案的 `document` 里连一个文本节点都没有。当时的机器验收 的 `lint` 因此不会打出
"每帧改 DOM 文本"的 NOTE（variant-a 用了 SVG `<text>`，被打出 3 处 NOTE，
但它的三条确定性检查都过了 —— 见 §9）。
