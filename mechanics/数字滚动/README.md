| 段 | 区间 | 画面 |

> 完全相同，等于一半时长是冻帧。加长靠的是**加大逐位错峰的间距**（STEP 0.25 → 0.90，
> 三段首尾相接而非挤在 1.6s 里）+ **中段可见的加速带**（`rollProg` 先加速后刹车，
> 不再是全程 easeOut），**不是把每个轮子放慢**。

## 1. 常见写法为什么在本 skill 里会坏

| 常见写法 | 坏在哪 | 本 skill 的 seekable 改法 |
|---|---|---|
| 每帧 `v += speed*dt` 再 `translateY(-v*H)`（累加器） | 结果依赖「跑了几帧」，掉一帧数字就偏；`__reelSeek(2.5)` 与「自然播到 2.5s」会得到两个值 | 删掉累加器，`v_d = tgt·(1−(1−u)^p)` 是 `t` 的**闭式函数**，任何 `t` 直接算 |
| 十位、百位各写一套带 `animation-delay` 的 CSS keyframes | delay 是墙钟；seek 时只把 `currentTime` 设过去，实际进度取决于样式解析顺序；改总时长要手改所有 delay | 错峰写成 `span(t, T0+d*STEP, T0+d*STEP+DUR)`，位号 `d` 是循环变量，加一位只改 `D` |
| `transition: transform .35s` 做落位回弹 | `transition` 由浏览器时钟驱动，seek 到 1.95 会停在过渡中间态且不可复现；lint 直接 FAIL | 回弹写成衰减正弦 `A·e^(−k·u)·sin(w·u)`，逐帧算最终值（§2 第 2 点） |
| 无时钟 `requestAnimationFrame` 里跑滚动 | 墙钟驱动 ⇒ 画面与 `t` 无关，反而能骗过「同 t 两次截帧一致」；lint 专门拦这条 | 全部走 `window.reelDraw(t)`，由 `seek.js` 在 seek 后调用 |
| `setInterval(() => tick(), 1000/30)` 推数字 | 定时器是墙钟，seek 不会重放它；lint 禁用 | `t` 就是时间轴本身，不存在第二个时钟 |
| 滚轮用 `Math.random()` 抖动 / 随机起始相位 | 同 `t` 两次截帧不同，determinism 直接 FAIL | 需要抖动时用 `hash(i)`；本特效所有量都是闭式的，连 `hash()` 都不需要 |
| **进度条走 CSS `scaleX` + 数字走 JS** | 同一量两个真值来源，seek 后必然对不上（比如条 71%、数字 128） | 只在 `reelDraw(t)` 里插值一次得 `num`，条宽 / 游标 / 百分比全部从它派生（§2 第 4 点） |
| 滚动结束后再写一次 `transform` 做回弹 | **同一元素同一帧写两次**，后写的把前写的滚动位置整个盖掉 | 滚动位移与两段回弹**在同一个表达式里相加**，最后只写一次（§2 第 3 点） |
| `animation: blink 1s infinite` 让游标呼吸 | `infinite` 被 lint 禁；且 CSS 动画与 `reelDraw` 是两条独立时间线 | 呼吸写成 `sin(2π(t−2.60)/1.70)` 的闭式，同一帧只写一次 `opacity` |
| `el.textContent = Math.round(v)` 做显示、同时另算一次滚动位置 | 两位小数进位时「显示的字」与「轮子停的位置」会差一格；两处独立插值必然漂移 | 字形由纸带位移唯一决定，`num`（条/百分比用）与纸带位移用**同一个 `v`** |

## 2. 关键技术点

### (1) 逐位错峰：固定时长、不同起点，所以「低位先停」

```js
var T0 = 0.30, STEP = 0.90, DUR = 1.28;
var EP = [2.6, 3.0, 3.4];                             // 每位自己的滚动曲线指数
var u = R.span(t, T0 + d * STEP, T0 + d * STEP + DUR);
var v = digitAt(d) * rollProg(u, EP[d]);              // 位 d 的连续值
```

位 `d`（0=个位）的窗口是 `[0.30+0.90d, 1.58+0.90d]`：**每位的时长都固定 1.28s，只是整体往后
挪**，所以个位 1.58 停、十位 2.48 停、百位 3.38 停——「低位先停」是**构造出来的**，不是给
每位调不同时长凑出来的。`EP` 递增（2.6 → 3.4）让高位中段更快、两头更慢，符合「位数越大跳得
越猛」的直觉，也是 SPEC 要求的「用不同 easing 指数」。

`STEP` 从第一版的 0.25 拉到 **0.90**（DUR 1.10 → 1.28）是把节奏做满的关键：三段窗口从
「几乎重叠」变成「首尾相接」（相邻重叠仅 0.38s），于是 0.3–3.6s 全程都有轮子在动，而不是
1.6s 内一起滚完、剩下 3s 全静止。**注意这是拉开错峰间距，不是把轮子放慢**——每位的实际
角速度反而更高（中段速度 = `tgt·p/dur`）。

滚动曲线刻意不用全程 easeOut，而是**先加速、中段最快、再刹车**的对称幂曲线：

```js
function rollProg(u, p) {          // 速度在 u=0.5 处最大，两端为 0
  if (u <= 0) return 0;
  if (u >= 1) return 1;
  return u < 0.5 ? 0.5 * Math.pow(2 * u, p)
                 : 1 - 0.5 * Math.pow(2 - 2 * u, p);
}
```

这条曲线在 `u=0.5` 两侧的导数同为 `p·1^(p-1)`，所以**速度连续、没有折点**（若直接拿
`easeIn` 拼 `easeOut` 会在中点出现速度跳变，画面上是轮子「顿一下」）。中段可见的加速带
正是复核意见要求的「看得出一个完整的滚动过程」。

这里刻意**保留 SPEC 的区间公式形状**，把具体数值按「最高位必须在 3.38 落定、且静态起手要留
0.30s」反解出来：`3.38 = 0.30 + 2×0.90 + 1.28`。四个常量里只有三个自由，第四个被约束定死，
所以改 `T0`/`STEP`/`DUR` 任意一个都不会让最高位跑出落位时刻——`T_LAND` 是从它们**推出来**的，
不是另写的字面量（这也是 §7.6 第 3 条「一个特效里不要出现两个开始/结束时刻」的做法）。

### (2) 回弹：三级衰减，参数各管一件事

```js
function damped(u, A, k, w) {          // u ∈ [0,1]
  return u >= 1 ? 0 : A * Math.exp(-k * u) * Math.sin(w * u);
}
var p = R.span(t, T0 + d*STEP + DUR, T0 + d*STEP + DUR + 0.26);  // 该位自己的落位窗口
var q = R.span(t, T_LAND, T_SNAP1);                              // 整体「咔」窗口
var y = stripY(v) + damped(p, 2.0, 8, 30) + damped(q, 5.0, 9, 52) + mic;
```

- `A` = 初始振幅（px）：一眼看到多大动静。该位轻响 2.0px、整体「咔」5.0px（整体更狠，
  因为那是「三根轮子一起顿一下」）。
- `k` = 衰减速率：`e^(−k·u)`，越大停得越快。取 8/9 时在 `u=0.4` 振幅已掉到 `e^(−3.2)≈4%`，
  `u=1` 时被强制归零，不会有残振留在结束态。
- `w` = 振荡角频率：一个窗口里振荡 `w/2π ≈ 4.8` / `8.3` 次。前者「闷一下」，后者「碎抖」；
  整体用大 `w` + 大 `k`，手感像金属卡榫。

`sin(w·u)` 在 `u=0` 处为 0，所以叠加是**连续**的；末端**必须**同时给 `u>=1 → 0` 与
`u=0 → 0` 两个边界，否则回弹会以非零位移「切断」，在 contact sheet 上表现为最后几格数字
突然上跳。

**微动收束段（3.60–4.20）刻意不用衰减振荡，改用单调鼓包**：

```js
var p   = R.clamp((t - (T_MIC_A0 + d * MIC_DELAY)) / MIC_SPAN, 0, 1);
var mic = MIC_A[d] * Math.sin(Math.PI * p);   // 两端为 0，中点最大（7 / 9.5 / 12 px）
```

第一版这里用的是衰减正弦，结果**峰值正好落在 contact sheet 的采样点之间**，15 格里后 5 格
看起来仍然一模一样（虽然逐字节不同）。单调鼓包在整段里都维持可读位移，两端又严格为 0，
既满足「落定后仍有一点点可读的变化」，又保证 4.20 之后完全静止。三位按 0.10s 相位差依次
下沉再回位，所以是小幅的级联而不是三根轮子一起跳。

### (3) 为什么「滚动」和「回弹」必须合成一个表达式再写一次

```js
/* ✅ 一次算完，一次写 */
var y = stripY(v) + damped(p, 2.0, 8, 30) + damped(q, 5.0, 9, 52);
wl.strip.style.transform = "translateY(" + y.toFixed(2) + "px)";

/* ❌ 写成两段：后写的把前写的滚动位置整个盖掉 */
if (t < T_LAND) wl.strip.style.transform = "translateY(" + stripY(v) + "px)";
if (t >= T_LAND) wl.strip.style.transform = "translateY(" + (stripY(v) + dy) + "px)";
```

这是这类特效最隐蔽的 bug：在**没有回弹的区间**（`t < T_LAND`）第二段不执行，一切正常；一进到
`t ≥ T_LAND` 第二段生效，只要它的表达式漏写 `stripY(v)`，画面就会跳到纸带顶端。合成一个
表达式后 `y` 是**这一帧的唯一真值**，不存在「谁盖谁」。

同理，位 `d` 的自己落位窗口 `p` 与整体回弹窗口 `q` 在最高位（`d=2`）时**时间上是重叠的**
（都在 `T_LAND=3.38` 附近），也必须在同一个 `y` 里相加，不能分两次写。

### (4) 一条时间线只有一个数值真值

```js
window.reelDraw = function (t) {
  var num = 0;
  for (var d = 0; d < D; d++) {
    var u = R.span(t, T0 + d*STEP, T0 + d*STEP + DUR);
    var v = digitAt(d) * rollProg(u, EP[d]);
    num += v * Math.pow(10, d);                       // 唯一的连续值
    /* …拼 y 并写一次 transform（见第 3 点）… */
  }
  var prog  = R.clamp(num / VALUE, 0, 1);
  var done  = prog >= 1;
  var shown = done ? 1 : Math.min(prog, 0.99);           // 未达成不许显示满格
  fillEl.style.width = (shown * 560).toFixed(3) + "px";   // 条宽
  capEl.style.left   = (shown * 560).toFixed(3) + "px";   // 端点游标
  pctEl.textContent  = Math.round(shown * 100) + "%";     // 百分比
};
```

条宽、游标位置、百分比三个派生量都来自 `num`。注意 `num` 是用**每一位的连续值**加权求和
得到的（不是 `Math.round` 出来的整数），所以中间帧的条宽能落在 76% 这种值上，而不是被量化
成整数跳变；同时纸带位移用的是同一个 `v`，字形不会和数字读数打架。

### (4b) 场景内仪表必须自洽

「同一个数值真值」不够——**状态文案也必须从同一个进度变量派生**，否则会出现
「条已经 100% 而右上角还写着 `COUNTING`」这种自相矛盾的画面（第一版就是这个毛病：
t≈1.72 条满格、文案到 2.07 才切，有约 0.35s 的窗口两者打架）。修法两条一起用：

```js
var prog  = R.clamp(num / VALUE, 0, 1);      // 唯一的进度
var done  = prog >= 1;                        // 到终点值 ⇔ 满格 ⇔ 达成
var shown = done ? 1 : Math.min(prog, 0.99);  // 未达成时显示量夹到 0.99
fillEl.style.width  = (shown * 560).toFixed(3) + "px";
pctEl.textContent   = Math.round(shown * 100) + "%";
statusEl.textContent = done ? "TARGET MET" : (prog > 0.90 ? "SETTLING" : "COUNTING");
```

两点关键：

1. **`prog` 到 1 的时刻就是最高位落位的时刻**（`T_LAND = T0 + (D-1)*STEP + DUR` 是推出来的，
   不是另写的字面量），所以「数字到位」「条满格」「切达成」是同一件事，不存在第二个结束时刻
   （§7.6 第 3 条）。
2. **未达成时把显示量夹到 0.99**：`Math.round(0.996 * 100)` 会显示 `100%`，而 `prog` 其实还
   没到 1——这是「条看着满了、文案却说还在跑」这个矛盾的真正来源。夹到 0.99 后，条最多
   554.4px、文本最多 `99%`，「看着满格」与「声称达成」在数学上不可能错开；最后 1% 在落位
   那一刻随机械回弹一起「咔」上去。

`variant-b` 的值到位分两步（量级曲线到 3.38 → 抹平末位残差到 3.60），所以它的 `done`
必须等两步都完成（`num >= VALUE && settle >= 1`），否则会出现「数字已是 1,280,000 但文案
还在 SETTLING」的反向矛盾。它的进度条按分隔线真实长度 1016px 换算——第一版写成 560px
（从主方案抄来的），结果 `100%` 只画到屏幕的 55%，是肉眼复核抓出来的。

**§7.6 第 4 条（concat 注意事项）**：本场景内的进度条 / 百分比 / 状态文案是**场景内仪表**，
写死在 `index.html` 里、以「本镜头自己的 0 秒」为原点。以后若把这些特效 concat 成整片，
它们应改走 kit 的 `gbar.json` + `REEL.offset`，由整片时间轴统一驱动，否则拼接后每段的
仪表都会从 0 重新开始。当前交付是单镜头独立成片，故仍用场景内仪表。

### (5) 纸带要「绕一圈」，否则 9→0 的进位会倒卷

如果纸带只有 `0123456789` 十格、靠 `translateY(-(v%10)*H)` 取模，那么 `v` 从 9.9 到 10.0 时
`v%10` 由 9.9 骤变 0.0，滚轮会**向后倒卷 9 格**——所有 odometer 实现最经典的翻车点。
本方案把纸带做成 13 格：

```js
var STRIP = ["9"];                                     // 索引 0：绕回来的 9
for (var s = 0; s < 10; s++) STRIP.push(String(s));    // 索引 1..10 = 0..9
STRIP.push("0"); STRIP.push("1");                      // 索引 11/12：绕出去的 0/1
var CI0 = (WIN - H) / 2;                               // 窗口比一格高，上下各露 37px 邻位
function stripY(v) {
  var f = Math.floor(v), frac = v - f;
  return -(((f % 10) + 1) * H + frac * H - CI0);       // cell = floor(v)%10 的纸带索引 = (f%10)+1
}
```

`v` 从 9.9 走到 10.0 时 `f%10` 由 9 变 0、纸带索引由 10 变 1，`translateY` 从 −(10+0.9)H
连续走到 −(1+0.0)H——位移差恰好方向与滚动一致，**没有回卷**。索引 0 与 11/12 保证窗口上下
露出的 37px 邻位在任意 `v` 都有字形可画，不会看到空白。

### (6) 运动模糊也必须是解析式（variant-a 的核心）

```js
/* 位 d 的解析速度：对 v(t)=tgt·(1−(1−u)^p) 求导 */
function wheelVel(d, t) {
  var u = (t - a) / (b - a);
  return tgt * p * Math.pow(1 - u, p - 1) / (b - a);
}
/* 残影 = 同一公式在 t−k·DT 上的值，离当前越远越淡，并随速度加权 */
var amp = Math.min(1, wheelVel(d, t) / 9);
for (var k = 3; k >= 1; k--) strip(x, wheelVal(d, t - k * DT), dy, GA[k-1] * amp, "#7fd2e0");
strip(x, wheelVal(d, t), dy, 1, "#e6f0f5");
```

`amp` 让残影**只在真的在滚的时候出现**：静止时 `vel=0` ⇒ 残影透明度 0，本体与残影完全重合，
画面干净。这是解析式拖尾相对「覆盖式拖尾」（每帧 `fillRect` 压暗一层，依赖上一帧）的关键
优势——后者在 seek 架构下必坏。

## 3. 踩坑记录

1. **DOM 从左到右成了「个位 → 十位 → 百位」，屏幕上读出来是 `821` 而不是 `128`。**
   第一版 `for (var d = 0; d < D; d++) frag.appendChild(win)`，`wheels[d]` 与 DOM 顺序一致，
   于是最左边是**个位**。（当时用旧时间轴探针，读到的是各位倒序的值，与目标 `128` 正好反）
   而我的浮点推算「`t=0.9` 时 v≈(8.50, 3.29, 2.40)」本身是对的，我只是
   没检查**它们被放进 DOM 的顺序**。改法：循环倒序 `for (var d = D-1; d >= 0; d--)`，
   但仍然写 `wheels[d]`，让 DOM 顺序与位号索引解耦，`reelDraw` 里 `d` 的含义不变。
   教训：**数值模型对 ≠ 屏幕对**，必须看图。

2. **数字没落在窗口中心，上沿被裁。** 第一版 `translateY(-((f%10)+1+frac)*H)` 把纸带里
   「当前格」的**上沿**对齐到了窗口上沿，视觉中心偏下、上方邻位几乎看不见。改成
   `-(((f%10)+1)*H + frac*H - CI0)`（`CI0=(WIN−H)/2`）后，当前格正中对齐窗口中心，上下各露
   37px 邻位，「滚轮」的立体感才出来；`t=0` 的 `000` 现在是三个 0 完整居中。

3. **当时的机器验收 只查「同一 t 两次截帧一致」，查不出「画面是错的」。** 上面两个 bug 都
   **完全确定性**——同 `t` 截两次逐字节一致，determinism 全 PASS，`sheet.png` 也照样生成。
   只有肉眼读数字才发现是 `821`。这印证了必须亲眼看图的原因：
   **客观检查管契约，肉眼管对错。**

4. **variant-b 最高位闸门永远只开到 11%。** 闸门按「量级跨越该位」驱动，第一版上界写死成
   `d+0.45`，即 `6.45`；但 `1,280,000` 的对数量级上限只有 `LV1 = 6.107`，于是
   `span(6.107, 6, 6.45) = 0.238`、`easeInOut(0.238) ≈ 0.113`，闸门宽度只有 `80 × 0.113
   ≈ 9px`。这个 bug 不报错、不 FAIL，只是百万位在整个片子里都被裁掉一半。靠 DOM 桩打出
   `w=9.08px`（目标 80px）才发现——它不是「宽一点窄一点」，而是**差一个数量级**。修法：把
   上界夹到 `LV1`。这也是我在没有 capture 的情况下先用 DOM 桩把每个中间量打出来的原因。

5. **variant-b 还有一个「真实里程表 vs 成片末帧」的取舍。** 耦合模型下
   `rotation_d = value/10^d`，末值 `1,280,000` 让百万位轮停在 `1.28` 格——即真实里程表上它
   确实**停在 `1` 与 `2` 之间**（20% 偏转，`2` 从下方露一条）。物理上对，但成片要求末帧
   数字落定，所以最后 0.40s 用 `settle` 因子把这 `0.28` 格的残差抹平（`v -= frac(VALUE/10^d)
   · settle`）。因为 `1,280,000` 能被 `10^5` 整除，只有百万位有残差，其余六位本来就精确。
   这是有意的「落位」而不是模型瑕疵。

6. **第一版 variant-a 稿子里留了死代码 + 一段假位移补偿。** `wheelValAt(x,k)` 返回常量 0 却
   参与残影绘制；落位回弹用「半透明重绘一层」近似（并不可靠）。整段重写成 `drawWheel(x, d, t)`
   一个函数，`dy` 作为 `strip()` 的垂直偏移参数同时作用于本体和所有残影，干净且真的对。

7. **当时的机器验收 第一次跑就 0 FAIL，但那是「契约合格」，不是「做完了」。** 我先把 README
   写成占位（内容只有「README 定稿中」）就跑验收，`deliver: 有 README.md` 直接 PASS——它只
   查文件存在，不查内容。所以 README 必须在**验收之后、交付之前**补全，不能拿验收器的 PASS
   当交付证明。

8. **当时那台机 ~4GB，导出被迫 `--jobs 1`。** 出片按 SKILL.md：`--jobs $(nproc)`，不要超过核数。
   本任务的三个导出是在**一个 `run_in_background` 作业里串行**跑完的，没有任何并发。

9. **「条已经满格、文案还说在进行中」——同一个进度量的两个真值来源。** 第一版状态文案用
   `t >= T_MET` 硬切，条宽用 `num/VALUE`，两个量各有各的时刻表：`t≈1.72` 时条已经 100%，
   文案却要到 2.07 才切 `LOCKED`/`TARGET MET`，中间约 0.35s 画面自我矛盾。更隐蔽的是
   `Math.round(0.996*100)` 会打印 `100%`，所以「看着满了」比「真的满了」还早一帧。
   修法见 §2(4b)：一个 `prog` 派生全部读数 + 未达成时显示量夹到 0.99。判定方法很便宜——
   DOM 桩逐点扫描，断言「不存在某帧同时满足 条≥满 与 状态≠达成」。

10. **把该动的区间拉长时，先想「错峰间距」而不是「减速」。** 第一版 15 格采样里有 8 格
    逐字节相同，问题不是轮子转得不够慢，而是三位的窗口重叠在 1.6s 内、后面 3s 全静止。
    把 `STEP` 0.25 → 0.90 拉开间距、再给中段一条加速带，画面立刻「有过程」；反过来若只把
    `DUR` 拉长，轮子会变成慢动作，手感更差。另外**首尾静止段要给硬上限**（这里是 0.30s 起手
   与 0.80s 定格），否则很容易又滑回「一半时长是冻帧」。

11. **变体从主方案「抄常量」时必须核对量纲。** variant-b 新增的进度条照抄了主方案的
    `(prog * 560)`，但它自己的分隔线长 1016px，于是 `100%` 只画到屏幕的 55%。这种 bug
    数字全对、lint 全过、verify 全 PASS，**只有看图才发现**——和踩坑 3 是同一类。

## 4. 方案对比

| | 主方案 index.html | variant-a canvas 残影 | variant-b 复合数字 |
|---|---|---|---|
| 画数字的方式 | 每格一个 DOM `<div>`，13 格 × 3 轮 | canvas `fillText` 逐轮重绘，每轮每帧 4 次绘制 | 同主方案，但 **7 位**且闸门可开合 |
| 滚动的表达 | `translateY` 复合表达式，逐位独立缓动 | 同公式，另加 3 个幽灵帧 `v(t−k·DT)` | 单一连续值取对数量级驱动，每位 = `num/10^d` + 残差抹平 |
| 运动模糊 | 无（实测 headless 下 `filter: blur()` 观感很差，见下） | 有，解析式：残影权重 ∝ 解析速度 | 有，`blur()` 随「每帧滚过几格」增长，并同步降透明度 |
| 错峰方式 | 逐位窗口 `[0.30+0.90d, 1.58+0.90d]`，低位先停 | 与主方案**完全一致**（共用骨架） | 无逐位错峰：所有位由同一个 `rollProg` 量级曲线驱动 |
| 皮 | 深色「记录仪」：墨蓝面板 + 琥珀强调 | 深色「频谱」：青绿强调 + 残影拖尾 | 浅纸「报表」：米白纸 + 墨字 + 墨绿块 |
| 额外信息 | 单位渐入、端点游标呼吸、三段状态文案 | 同主方案 | `+` 号、千分位逗号、单位色块、环比注脚 |
| 实现成本 | 低：纯 DOM，`reelDraw` 约 40 行 | 中：clip + 上下渐隐 + 幽灵帧 + canvas 几何 | **高**：量级映射 + 逐位闸门 + 逗号闸门 + 残差抹平 + 模糊量 |
| 帧数/CPU | 150 帧 × 3 轮 DOM 写，最快（137 KB，导出 ~40s） | 150 帧 × 12 次 `fillText`（135 KB，导出 ~45s） | 150 帧 × 7 轮 DOM 写 + 7 个 `filter`，最慢（220 KB，导出 ~50s） |
| 末帧数值 | `128`（`qa-04.png` 手读确认） | `128`（同上） | `+1,280,000`（同上，千分位位置正确） |
| 可读性 | **最好**：数字大、对比强、信息点少 | 好，但残影让正在滚的轮子略糊 | 好，但一屏信息点更多（标题/环比/单位块/两条注脚） |
| 复用性 | 高：换 `VALUE` 一个常量即可（`D` 目前是手写 3） | 高：同主方案，canvas 尺寸随 `D` 变 | 中：要同时调 `NUM0` 才能让「起手 1,000」成立 |

**推荐主方案。** 理由：

1. **它把「逐位独立缓动」表达得最直白。** 观众一眼看到的是「个位先停、百位还在滚」，
   也就是里程表真正的语义；variant-b 用一条统一的量级曲线，其实**丢掉了逐位错峰**，
   滚起来更像「一个数字在缩放」而不是「一排轮子在转」。
2. **DOM 版的运动模糊本来就不该做。** 主方案第一稿曾用 `filter: blur(vel·0.1)` 做糊化，
   实测在 headless Chromium（`--disable-gpu`）下几乎看不出区别，只会让字形发虚；真正有效的
   模糊是 variant-a 的**残影**，而且残影在 DOM 与 canvas 上都是解析式的。既然主方案的目标
   是「读得清」，就不加糊——主方案最终只保留 ≤2.6px、且只在个位高速段生效的一点点 `blur`。
3. **末帧最重要。** 主方案末帧只有一组主体（`128` + 单位）加一条满格条，是 12 条视觉标准里
   「主体唯一 / 末帧成图 / 留白呼吸」三条同时最稳的一版；variant-b 末帧有 6 个信息点，
   缩略图尺寸下已接近「同一时刻 ≤ 3 个信息点」的上限。

② 主体（三位滚轮 + 单位 + 条与百分比，唯一在动的东西）、③ 页脚一行技术注（静态、不参与

## 6. 视觉质量评分表自评

| # | 检查项 | 自评 | 依据 |
