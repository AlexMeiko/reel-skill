## 0. 核心证明：点亮必须是一条行波

把路径按弧长参数化，`s ∈ [0, L]`。本特效要求「弧长 `s` 处的点亮时刻」是

```
T(s) = t₀ + s / v          （v 是传播速度，px/s，恒定）
```

这是一个**沿路径匀速前进的行波**。反过来问「时刻 t 时哪些弧长已经亮了」：

```
{ s : T(s) ≤ t } = [0, min(L, v·(t − t₀))]
```

因为 `T(s)` 对 `s` 严格单调，所以已点亮的集合永远是**从起点开始的一段前缀区间**，
其长度是 t 的**闭式函数**：

```
litLen(t) = clamp(v · (t − t₀), 0, L)
```

于是「点亮」这件事在任一帧只需要**一次 `stroke-dasharray` 写入**（或对采样折线做一次前缀截断），
不需要任何跨帧状态：

```js
var litLen = reel.clamp(V * (t - T0), 0, L);   // ✅ 真值是 t 的函数
var dash   = litLen.toFixed(2) + " " + L.toFixed(2);
glow.setAttribute("stroke-dasharray", dash);
tube.setAttribute("stroke-dasharray", dash);
core.setAttribute("stroke-dasharray", dash);
```

```js
litLen += V * dt;                              // ❌ 累加器：真值变成"历史"的函数
```

累加器的坏处不是"不准"，而是**它在 seek 架构下是错的**：当时的机器验收 的换路径检查
（先经 0/25% 再到达 t=2.5 vs 直接 seek 到 2.5）会让同一个 t 得到两张不同的画面。
本方案里 `litLen` 是纯函数，两条路径必然给出同一张图。

**唯一的速度参数**是 `DRAW`（传播时长 2.2s）：

```
v = L / DRAW        全管亮起的时刻 = t₀ + L/v = t₀ + DRAW = 0.40 + 2.20 = 2.60s
```

所以「通电时刻」不是第二个开始时刻，而是**从同一个 v 推出来的**（场景内仪表规则：
一个特效里不许出现两个开始/结束时刻）。`L` 由浏览器在 load 时用 `getTotalLength()` 量出，
本机实测 **L = 3301.83 px**（几何全部是直线 + 四分之一圆弧，可手算复核，见 §4），
于是 **v = 1500.83 px/s**。

## 1. 常见写法为什么在本 skill 里会坏

| 常见写法 | 坏在哪 | 本库的 seekable 改法 |
|---|---|---|
| `stroke-dasharray` 配 CSS `@keyframes` + `infinite` 闪烁 | `infinite` 让末帧回到第 0 帧，永不是结束态；seek 也不会等动画 | 每帧在 `reelDraw(t)` 里写 `stroke-dasharray`；闪烁改成 `t` 的闭式函数，末帧自然稳定 |
| `litLen += v * dt`（`requestAnimationFrame` 累加） | 真值是历史的函数；换 seek 路径同一 t 给出不同画面；掉帧永久落后 | `litLen = clamp(v*(t−t0), 0, L)` —— 只给 t 就能算出这一帧 |
| `Math.random()` 做闪烁 | 同一 t 两次截帧不一致（当时的机器验收 determinism 直接 FAIL） | `hash(floor(t*RATE))` 时间量子，同一量子同一取值 |
| `filter: drop-shadow` 分别挂在多个 DOM 元素上 | 每个元素一次离屏模糊，帧成本线性膨胀（本库实测：粒子聚合的 DOM+drop-shadow 变体 8m52s vs canvas 主方案 1m31s） | 光晕只做**一次**：SVG 里一条 22px 宽、`blur(12px)` 的路径；玻璃反光点用纯色短线，不挂滤镜 |
| `transition` 补间驱动点亮 | transition 是墙钟补间，seek 不会等它跑完 → 画面滞后于 t | 全部走 `reelDraw(t)` |
| 每帧改 DOM 文本显示弧长读数 | Chromium 字形栅格化缓存会在高负载下产生 1/255 抖动，导致"同 t 两次不一致"（PATTERNS §6.1，故障文字实测） | 逐帧变化的读数**画进 canvas**（`ctx.fillText`），DOM 里只留静态文案 |
| 逐字用 `TTS`/`setTimeout` 排队点亮 | 排队 = 跨帧状态；seek 到 2.5s 时前面 10 个 timeout 根本不会补跑 | 每个字的点亮时刻写成常量 `t₀ + s_k/v`，在 `reelDraw` 里按 `litLen` 比较 |
| 用 `t / REEL.duration` 当进度分母 | 末帧是 `(帧数-1)/fps`，永远差 1/fps，读数停在 99% | 字面量结束时刻（本片 `T_ON = t₀ + DRAW = 2.60`，`litLen` 在 2.60s 就 clamp 到 L） |

## 2. 关键技术点

### 2.1 三层霓虹必须同源（同一个 `litLen`、同一个 `lum`）

霓虹感 = 三层叠加。三层**必须共用同一个进度**，否则会出现"光晕已经到头、管身还没到"这种
失同步 —— 这是本特效最容易踩的坑。代码里它们只有一次插值：

```js
// ① 行波：唯一真值
var litLen = reel.clamp(V * (t - T0), 0, L);

// ② 嗡闪：时间量子 + 解析衰减包络，只调制亮度
var u = reel.span(t, T_ON, T_ON + FLK);
var env = Math.exp(-3.0 * u), buzz = Math.abs(Math.sin(26 * u));
var q = Math.floor(t * RATE), jit = 0.66 + 0.34 * hash(q * 2.3 + 7.1);
var flick = 1 - 0.60 * env * buzz * jit;
var lum = flick * breathe * hum;              // breathe / hum 见 §2.5

// ③ 三层：同一个 dash、同一个 lum，每元素每帧只写一次
var on = reel.span(litLen, 0, 6);            // 见 §5 踩坑 1
var dash = litLen.toFixed(2) + " " + L.toFixed(2);
glow.setAttribute("stroke-dasharray", dash);
tube.setAttribute("stroke-dasharray", dash);
core.setAttribute("stroke-dasharray", dash);
glow.style.opacity = (0.55 * lum * on).toFixed(4);
tube.style.opacity = (1.00 * lum * on).toFixed(4);
core.style.opacity = (0.85 * lum * on).toFixed(4);
```

三层参数（同一段 `d`，宽/色/模糊不同）：

| 层 | stroke-width | 颜色 | 其它 | 作用 |
|---|---|---|---|---|
| `#glow` | 22 | `#ff3f86` | `filter: blur(12px)`，opacity 0.55 | 玻璃管外的辉光 |
| `#tube` | 8 | `#ff2f7e` | opacity 1.00 | 管身（真实宽度） |
| `#core` | 2.4 | `#fff1f7` | opacity 0.85 | 灯芯高光 |
| `#tubeOff` | 8 | `#ff4088` | opacity 0.11，**没有 dash** | 未通电的玻璃管（静态壳） |
| `#spec line` | 2.2 | `#fff` | 每 150px 弧长一根，位置 load 时算一次 | 玻璃反光点 |

光晕宽度 22 ≈ 管身 8 的 2.75 倍，模糊半径 12 约为管宽 1.5 倍 —— 这个比例下
辉光是"包住管子的一层"而不是"糊成一团"，主体始终可读（`probe/` 里可复核）。

### 2.2 `getPointAtLength` 探头：位置与进度共用同一个 `litLen`

```js
var hp = tube.getPointAtLength(litLen);                  // 波前所在的点
probe.setAttribute("transform", "translate(" + hp.x.toFixed(2) + "," + hp.y.toFixed(2) + ")");
var headOp = (litLen > 2 && litLen < L - 4) ? (1 - reel.span(p, 0.90, 1.0)) : 0;
probe.style.opacity = (headOp * lum).toFixed(4);
```

探头不是"另一条动画"：它就是 `litLen` 那一点的坐标。淡出用 `span(p,0.90,1.0)`，
p 到 0.9 之后逐渐消失，`litLen ≥ L` 之后严格为 0 —— 末帧不会留一个孤零零的光点。

### 2.3 玻璃反光点：波前扫过才亮（同样只由 `litLen` 派生）

```js
for (var i = 0; i < SPECS.length; i++) {
  var sp = SPECS[i];
  var o = (reel.clamp((litLen - sp.s) / 90, 0, 1) * 0.55 * lum).toFixed(3);
  if (o !== sp.o) { sp.el.style.opacity = o; sp.o = o; }   // 值没变就不写，省一次 style recalc
}
```

每根反光线的弧长坐标 `sp.s` 在 load 时用 `getPointAtLength` 量一次，
方向用法线上 ±4.2px 的短线（保证是"管子上的反光"而不是"飘在外面的点"）。

### 2.4 招牌字：亮度浮起，字形不动

```js
brand.style.opacity = (reel.clamp((litLen - BRAND_S) / 150, 0, 1) * (0.42 + 0.58 * lum)).toFixed(4);
```

`BRAND_S = 470` 是"字的弧长位置"（顶边中点 ≈ 673px，提前 200px 起亮）。
字形、字号、位置**全程不变**，只改 opacity —— 这既是设计（霓虹招牌的通电感），
也是避坑（PATTERNS §6.3：改字宽会带来亚像素抖动）。0.42 的下限保证嗡闪时字仍可读。

### 2.5 闪烁的确定性写法（本特效的硬要求）

```js
function hash(i) { var x = Math.sin(i * 127.1 + 311.7) * 43758.5453123; return x - Math.floor(x); }

var RATE = 13;                                   // 时间量子频率，刻意不取 30/60
var q    = Math.floor(t * RATE);                 // ← 时间量子
var jit  = 0.66 + 0.34 * hash(q * 2.3 + 7.1);    // ← 量子内的确定性伪随机
var u    = reel.span(t, T_ON, T_ON + 1.30);
var flick = 1 - 0.60 * Math.exp(-3.0 * u) * Math.abs(Math.sin(26 * u)) * jit;

// 尾段不能死：解析式呼吸 + 常驻微嗡，两者都只乘 opacity
var breathe = t > BREATH_AT ? 1 + 0.045 * Math.sin((t - BREATH_AT) * 3.6) : 1;
var hum     = 1 - 0.016 * (0.25 + 0.75 * hash(q * 1.7 + 2.9));
var lum     = flick * breathe * hum;
```

五条规矩，缺一条就会坏：

1. **随机源是 `hash(整数)`，不是 `Math.random()`** —— 同一 `t` 必须得到同一画面
   （随机必须是确定性伪随机；`Math.random()` 会被 lint 直接判 FAIL）。
2. **量子化，不是 `hash(t)`** —— 连续 t 每次都不同，会退化成逐帧噪声；
   `RATE = 13Hz` 时每个量子跨 ~2.3 帧，人眼能看出"嗡"的节拍，掉帧也不变样（PATTERNS §1.3）。
   不用 30/60Hz 是因为与帧率同频会退化成逐帧噪声。
3. **`u = 0` 时严格回到 1** —— 包络是 `exp(-k·u)·|sin(ωu)|`，`u=0` 时 `sin(0)=0`，
   所以 `flick(T_ON) = 1`，起笔之前和通电瞬间都是无闪烁的，不会突然变暗。
   窗口取 1.30s、衰减取 `k=3.0`（第一版是 0.90s / `k=5.2`），是为了让"嗡"变成
   **数得出的两下**（低谷落在 t = 2.68s / 2.84s，第三下已经衰减到看不出），
   而不是 0.27s 内挤三下的"滋"一声。
4. **闪烁只乘 `opacity`，绝不碰几何** —— `stroke-dasharray`、`getPointAtLength` 的位置、
   招牌字的 transform 全部只由 `litLen` 决定。抽任意一帧，三层长度都严格相等
   （画面里那行 `dash 3/3` 就是每帧从三层 DOM 上读回来比对的）。
5. **尾段不能真的停**（PATTERNS §6.6 的推广）—— 起振后除了解析式呼吸（±4.5%，周期 1.75s），
   还叠了一条 13Hz、幅度 1.6% 的**常驻微嗡**（同一个时间量子）。
   两者都只乘 `opacity`，所以"末帧是稳定的结束态"和"尾段不留死帧"可以同时成立：
   实测最长静止段 0.40s，静止占比 15%（起手 0.4s 静止壳）。

## 3. 方案对比（含实测导出耗时）

三个方案都把同一条行波定律实现了一遍，差别在**材质实现**和**代价**。
实测环境：8 核 / 3.5GB 可用，`capture.mjs --jobs 1`，150 帧 @1280×720@30fps。

| | 主方案 `index.html` | 变体 A `variant-a.html` | 变体 B `variant-b.html` |
|---|---|---|---|
| 材质实现 | SVG 三层路径 + `filter: blur(12px)` | DOM `<span>` + 5 层 `text-shadow` | canvas `shadowBlur` ×2 遍 |
| 行波的画法 | 一次 `stroke-dasharray` 写三层 | 每个字的弧长 `s_k` 与 `litLen` 比大小 | load 时展平成 835 点折线，按弧长前缀截断 |
| 离散/连续 | 连续 | **离散**（6 个字，逐字翻转） | 连续（步长 4px 的离散采样 + 前沿插值） |
| 光晕质量 | 最像真霓虹（模糊核均匀、不随路径方向变化） | 最亮、最"灯箱"，字芯容易过曝 | 光晕偏硬偏平，宽笔画的阴影会糊 |
| **实测导出耗时**（两次） | **2m22.8s / 2m27.8s** | **2m19.7s / 2m16.7s** | **2m38.1s / 3m07.5s** |
| 每帧写入量 | 3 个 dasharray + 3 个 opacity + ~21 个反光点 | 6 个 opacity + 2 个 transform | 4 次 path stroke（2 次带 shadowBlur） |
| 可读性/复用性 | 几何只写一遍（`D` 常量），三层引用同一段 `d`，最好维护 | 字形与排版都由文本流控制，最好改文案 | 几何是 JS 数组，最好与其它 canvas 特效同屏合成 |
| 玻璃反光 | 有（每 150px 一根） | 无 | 无（`shadowBlur` 已经吃掉细节） |

### 3.1 实测导出耗时的结论（与当时性能警告对照）

每个方案各跑两遍，`--jobs 1`，互不并发，各 150 帧（30fps × 5s）：

| 方案 | 第 1 遍 | 第 2 遍 | 均值 | 每帧（均值） | run-to-run 波动 |
|---|---|---|---|---|---|
| 主方案（SVG `blur(12px)` × 1 条路径） | 2m22.8s | 2m27.8s | 2m25.3s | 0.97s | 3.5% |
| 变体 A（DOM，6 字 × 5 层 `text-shadow`） | 2m19.7s | 2m16.7s | 2m18.2s | 0.92s | 2.1% |
| 变体 B（canvas，2 遍带 `shadowBlur` 的 stroke） | 2m38.1s | 3m07.5s | 2m52.8s | 1.15s | **18.6%** |
| （参考）主方案在宿主上还有别的子代理同时跑时 | 2m44.1s | — | — | 1.09s | — |

> 注意变体 B 两遍差了 18.6%（2m38s → 3m07s），**同一份代码没改过**。
> 这说明本机（8 核被多个子代理共享）的 run-to-run 噪声比三个方案之间的差异还大。
> 所以下面所有耗时结论都只按"量级"读，不按百分比排名。
> 三次导出的原始 `time` 输出在 `export-run0-main.log` / `export-run1-all.log` / `export-run2-all.log`。

**结论一：三者同量级（0.92–1.15 s/帧，均值极差 25%）。**
这跟当时记录里"DOM + drop-shadow 变体 8m52s vs canvas 主方案 1m31s"的 5.8 倍差距完全不同 ——
因为差距**不是**"DOM vs canvas vs SVG"造成的，而是**"带模糊的绘制对象个数"**造成的：

| 写法 | 带模糊/阴影的对象数 | 实测 |
|---|---|---|
| 粒子聚合的 DOM 变体：每个粒子一个 `filter: drop-shadow` | 几十~上百个 | 8m52s（532s） |
| 主方案：一条 `blur(12px)` 的路径 | **1** | 2m25s（145s） |
| 变体 B：两遍 `shadowBlur`（34px / 12px）的 stroke | **2** | 2m53s（173s） |
| 变体 A：6 个字各 5 层 `text-shadow`（模糊半径 6–114px，但**区域只有一个字大**） | 30 层 / 小面积 | 2m18s（138s） |

也就是说：成本 ≈ **模糊的面积 × 层数**，跟用什么技术栈关系不大。
本特效把辉光收成"一条路径 + 一次模糊"之后，三个方案都只有粒子聚合那种写法的 **26–33%**
（145s / 532s = 27%）。这正是当时那条性能警告想要的结果：**能一条路径解决，就不要每个元素各挂一个滤镜。**

**结论二：主方案不是最慢的**（我原本以为 SVG `blur` 最贵，实测 0.97 s/帧，比变体 B 快）。
变体 B 是三者里最慢的，因为 canvas 的 `shadowBlur` 每帧都要对整条已画路径重做两次大核模糊，
而且没法像 SVG 滤镜那样跨帧复用光晕形状。

**推荐主方案**（不是为了快，是为了质感与最难写坏）：

1. 光晕质量最好：SVG `blur` 是各向同性的高斯核，沿路径方向不会出现 canvas 阴影那种方向性偏色；
2. 三层严格同源最难写坏：`d` 只有一个真值，`dasharray` 只有一个字符串，抽帧时长度必然一致；
3. 成本与另外两个同量级：2m25s 的导出里，`blur(12px)` 那条路径是唯一的重活，且只有一条。

变体 A 略快（2m18s，比主方案快 5%，在噪声范围内），但它只适合"文字型霓虹"，
且字芯过曝问题需要额外压；想要廉价霓虹字就选它。
变体 B 最慢且光晕质感最硬，好处是几何是纯 JS 数组，容易和别的 canvas 特效同屏合成。

## 5. 踩坑记录（都是实际报错/实际画面）

### 5.1 `stroke-dasharray` 里长度为 0 的 dash + `round` 线帽 = 一个直径 8px 的圆点

**症状**：`t=0.2s`（还没起笔，`litLen = 0`）的画面里，路径起点 `(264,440)` 上有一个
**亮粉色圆点 + 白色芯**。但代码里 `headOp = (litLen > 2 && …) ? … : 0`，探头应该是 0。

**定位**：把 `t=0.2s` 的帧按 (230,410)-(320,468) 裁出来放大看，亮斑直径正好等于管身宽度。
`stroke-dasharray: "0.00 3302.00"` 里第一个 dash 长度是 0，SVG 规范下它会配合
`stroke-linecap: round` 渲染成一个**直径 = stroke-width 的圆点**（三层各画了一个，
`#glow` 的模糊把它放大成一大团）。

**修法**：`litLen → 0` 时把三层**一起**用 opacity 闭掉，而不是只依赖 dash 长度：

```js
var on = reel.span(litLen, 0, 6);      // 0→6px 内平滑起亮
glow.style.opacity = (0.55 * lum * on).toFixed(4);   // 三层同一个 on
```

顺带得到一个意外的好处：起笔那 4ms 是一个平滑的"打火"，比硬切进去自然。

### 5.2 canvas 版：`stroke()` 内部重设 `globalAlpha`，把 12% 的暗管画成了 100%

**症状**：变体 B 在 `t=1.2s`（`ARC 1201 / 3302`，只该亮 36%）看起来**整条都亮了**。
对比 `t=4.9s` 的帧几乎看不出差别 —— 典型的"静默失败"：不报错，只是参数没生效。

**定位**：封装函数 `stroke(until, width, color, blur, shadowColor, alpha)` 内部第一句就是
`ctx.globalAlpha = alpha;`。调用处写的是

```js
ctx.save(); ctx.globalAlpha = 0.12; stroke(L, 8, "#ffa42e", 0, "", 1); ctx.restore();
//                              ↑ 传进去的 alpha 是 1 → 把外层的 0.12 覆盖掉了
```

外层的 `save/restore` 一点用都没有，因为真正的写入在函数体内部。

**修法**：把透明度当作参数传进去，删掉外层的手工设置：
`stroke(L, 8, "#ffa42e", 0, "", 0.12);`

### 5.3 canvas 版的 HUD 和 DOM 版公式文案叠在一起

**症状**：变体 B 左下角出现"重影"——`ARC` 数字压在「几何在 load 时被展平成…」上。

**原因**：主画布上的读数画在 `x=120`，而 DOM 的 `.law` 也定位在 `left:120px`。
**修法**：读数统一画到 `x=820`（与变体 A 的 `#hud` 同一个位置）。
教训：canvas 和 DOM 是两套坐标系，**排版对齐要显式写死同一组数字**，不能靠"看起来差不多"。

### 5.4 第一版的"嗡闪"挤成了一声"滋"，尾段还近乎死掉

**症状**（看 `sheet.png` 的第 8–14 格发现的）：第一版 `FLK = 0.90s / k = 5.2`，
`|sin(26u)|` 在 0.9s 里能挤出三个低谷（t = 2.65 / 2.76 / 2.87），间隔只有 0.11s
—— 30fps 下相邻两个低谷只隔 3 帧，人眼读到的是"滋"的一声，不是 SPEC 要的"嗡地闪两下"。
同时因为包络衰减太快（`exp(-5.2u)` 在 0.5s 就掉到 0.07），2.6s 之后整片只剩 ±2.8% 的呼吸，
contact sheet 第 8–14 格几乎一模一样 —— 虽然 `density` 过了（最长静止段 0.53s），
但"15 格要能看出连续变化"这一条在人眼下是不合格的。

**修法**：
- 窗口拉长到 `FLK = 1.30s`、衰减放慢到 `k = 3.0` → 低谷落到 t = 2.68 / 2.84 / 2.99，
  间隔 0.16s，**前两下清楚、第三下已经衰减**，读起来正好是"嗡·闪两下"；
- 呼吸幅度 2.8% → 4.5%、周期 2.4s → 1.75s；
- 再叠一条 13Hz、1.6% 的**常驻微嗡**（复用同一个时间量子 `q`），
  让"末帧稳定"和"尾段有像素级变化"同时成立。

改完复看 `sheet.png`：第 8–14 格能看出亮度在缓慢起伏（呼吸）而不是 7 张同一张图。
教训：**`density` 这个指标（YAVG 整帧平均）抓不到"动得太少"**（PATTERNS §7.3 已经写明），
"尾段是不是死的"只能靠把 sheet 当 15 张封面看 —— 这次就是靠看图抓到的。

### 5.5 lint 的 `textContent` NOTE

第一版用 `vline.textContent = "v = …"` 在 load 时写一次速度值，
当时的机器验收 报 `[NOTE] 有 1 处每帧改 DOM 文本`。虽然 NOTE 不计入判定，
但它统计不出"每帧"和"只在 load 写一次"的区别，于是改成
`vline.replaceChildren(document.createTextNode(...))`，把 NOTE 清掉。
逐帧变化的读数本来就已经全部画在 canvas 里（PATTERNS §6.1）。

## 8. 与 SPEC 的差异（都是有意的，逐条说明）

| SPEC 里写的 | 实际实现 | 为什么 |
|---|---|---|
| 嗡闪 `flick = 1 − 0.55·exp(−6u)·\|sin(24u)\|` | `1 − 0.60·exp(−3.0u)·\|sin(26u)\|·hash(floor(t·13))` | 任务书硬性要求"闪烁必须是确定性的时间量子 `hash(floor(t*RATE))`"。保留了 SPEC 的解析衰减包络（`u=0` 时严格为 1，保证末帧稳定），把它乘上量子抖动；同时把窗口从 0.90s 拉到 1.30s，让"嗡"从一声"滋"变成数得出的两下（§5.4） |
| 高光层用 `stroke-dasharray` 做断续玻璃反光 | 三层 dasharray **只表示点亮长度**；断续反光改成沿弧长每 150px 一根独立白色短线 | 若高光层用两套 dash 语义，就无法用"三层 dasharray 严格相等"来客观检查同源性（画面里的 `dash 3/3`）。改用独立短线后，反光点仍然只由 `litLen` 派生（波前扫过才亮） |
| 探头亮点 `p >= 1` 时淡出 | `p ∈ [0.90, 1.0]` 平滑淡出 | 硬切会在末段留下"光点突然消失"的一帧；平滑淡出后 `litLen ≥ L` 时严格为 0 |
| "一笔连写的霓虹字/图形" | 一笔连写的**招牌框 + 心电波形**，框内配招牌字「霓虹」 | 单笔连写的中文字形不可行；选"圆角框 + 心电波形"是因为它既是常见霓虹招牌形制，又让波前要走过"直线→圆角→折线"三种曲率（更能暴露"每到拐角就失同步"的写法）。招牌字「霓虹」由波前经过时浮起，仍是同一个 `litLen` 派生 |
| SPEC 未提变体的行波画法 | 变体 A 用"逐字弧长比较"，变体 B 用"折线前缀截断" | 三个方案各用**一种不同的机制**实现同一条 `T(s)=t₀+s/v`，用来证明"定律与实现无关" |
