**一句话**：一个终端窗口里，命令行被逐字敲入 → 停半拍 → 输出逐行刷出（其中一行是红色的报错）
→ 整段输出被框选；随后切到编辑器视图（variant-a），代码逐行出现并语法高亮。

**本特效要证明的事**：把「队列 + 定时器」这种程序式动画翻译成 seek 架构的通用手法 ——
**整个「打字 / 逐行 / 停顿 / 报错 / 框选」时间轴在 load 时被预计算成一张字面量表**，
播放期只剩两件事：**二分查到当前条目**、**算出条目内的字符数**。
没有任何累加器、定时器、随机数。**禁止「每帧 `typedLen++`」。**

### 3.1 展开：load 时一次，纯计算

```js
function buildSchedule(script, tText) {
  var L = [], row = 0, t = tText;                 // t = 累计时刻（唯一的游标）
  for (var i = 0; i < script.length; i++) {
    var s = script[i], kind = s.kind, len = s.text.length;
    var r, t0, t1 = 0;
    if (kind === "pre") { r = row; row += 1; t0 = 0; }              // t=0 就在画面里
    else if (kind === "prompt") { r = row; t0 = 0; }                // type 与它同一行
    else if (kind === "type") { r = row; row += 1; t0 = t; t1 = t + len / s.cps; t = t1; }
    else if (kind === "pause") { r = Math.max(0, row - 1); t0 = t; t1 = t + s.dur; t = t1; }
    else if (kind === "mark") { r = Math.max(0, row - 1); t0 = t; t1 = t + s.dur; t = t1; }
    else { r = row; row += 1; t0 = t; t1 = t + s.dur; t = t1; }     // out / err
    L.push({ row: r, kind: kind, text: s.text, t0: t0, t1: t1, cps: s.cps || 0 });
  }
  return L;
}
```

### 3.2 二分查找：给定 t，O(log 22) 定位当前条目

```js
function lineIndexAt(t) {
  var lo = 0, hi = N - 1, best = 0;
  while (lo <= hi) {
    var mid = (lo + hi) >> 1;
    if (LINES[mid].t0 <= t) { best = mid; lo = mid + 1; } else { hi = mid - 1; }
  }
  return best;
}
```

行内进度是**量子化的解析式**，不是累加：

```js
function charsShown(idx, t, i) {                  // 条目 idx 在 t 时刻已显示几个字符
  var e = LINES[idx], n = e.text.length;
  if (idx > i) return 0;                          // 还没轮到它
  if (e.kind === "type") n = Math.floor((t - e.t0) * e.cps);           // ← 逐字
  else if (e.kind === "out" || e.kind === "err")
    n = Math.floor(span(t, e.t0, e.t1) * e.text.length);               // ← 逐行刷出
  return n < 0 ? 0 : (n > e.text.length ? e.text.length : n);
}
```

画的时候把 `0..i` 全部条目各画一次（`j < i` 画全量，`j === i` 画部分），
所以「输出行一旦刷出就一直留着」也不需要任何状态。

## 1. 常见写法为什么在本 skill 里会坏

| 常见写法 | 坏在哪 | 本 skill 的 seekable 改法 |
|---|---|---|
| `setTimeout`/`setInterval` 队列：`queue.shift()` 后再排下一行 | 位置取决于「页面活了多久」。seek 到 `t=3.0` 时队列里还剩什么完全看运气（反例 A3：同 t 2 次截帧不一致） | **load 时一次展开成 `LINES`**，`t0/t1` 是字面量算出来的绝对时刻；播放期不排队 |
| 每帧 `typedLen++` / `i++` | 跨帧状态，是「确定性地错」：它照样能过「同 t 两次截帧一致」，只有**换 seek 路径**才抓得住（PATTERNS §8） | `n = floor((t - t0) * cps)` —— `t` 的纯函数，换路径必然同值 |
| CSS `steps()` / 逐字宽度动画 | 只能做「一条线打一个字」，做不出「36 行的绝对时刻由前一行决定」；而且延迟要手改，和 JS 的数字会失同步 | 时间全部进 `LINES`，CSS 一行动画都不写（lint 报告「无 CSS animation」） |
| 光标 `animation: blink 1s infinite` | `infinite` 让末帧闪回起点；而且闪烁相位与 `t` 无关，seek 到哪都可能停在同一态 | 方波 `Math.floor(t*2) % 2`，写在 `reelDraw` 里（§2.4） |
| `transition: height` 做框选生长 | 墙钟补间，seek 不等它跑完，画面滞后于 `t`（反例 A5） | 高度由 `span(t, t0, t1)` 直接算出，每帧写一次终值 |
| `Math.random()` 逐字抖动 / 乱码 | 不可复现，同 t 两次截帧必不同（反例 A2） | 本特效不需要随机；要也得走 `hash(i)` + 时间量子 |
| `requestAnimationFrame` 里读墙钟推进打字 | 画面与 `t` 无关（反例 A1：它能骗过「同 t 两次截帧」） | 不写 rAF；唯一入口是 `reelDraw(t)` |
| 每帧改 DOM 文本（`el.textContent = prefix`） | Chromium 字形缓存栅格化的 **1/255 抖动**，同 t 两次截帧偶发不一致（PATTERNS §6.1，只在系统高负载下复现） | **主方案把整幅终端画进 `<canvas>`**，一个字节 DOM 文本都不改（§2.5） |
| 每行各写一套 `animation-delay` | 改总时长要手改 19 处，且和 `reelDraw` 里的滚动/光标数字迟早对不上 | 滚动量、光标位置、框选几何全从同一次 `lineIndexAt(t)` 派生 |

## 2. 关键技术点

### 2.1 终端整幅画进 canvas：为什么（这条是踩坑换来的）

本特效是 §6.1 的高危区：光标每帧移动、已打字数每帧变 —— 如果这些文本挂在 DOM 上，
每帧都要 `textContent = prefix`，就会踩到「字形缓存 1/255 抖动」。
`故障文字/README.md §5.1` 已经把这个坑的排查链写透了（差异只有几百字节、`maxdelta=1/255`、
固定在同一小块像素、只在 8 路 CPU 满载时复现；把会变的读数挪进 canvas 后 20/20 逐字节一致）。

所以主方案走最彻底的那一档：**窗口、标题栏、19 行终端文本、光标、框选、标签全部 `ctx.fillText` /
`fillRect` 画进一张 1280×720 的 canvas**，DOM 里只有 `.stage` + `<canvas>`，**零处 DOM 文本写入**。

- 代价：代码里全是 `ctx.fillText`，不如 DOM 好改字。
- 收益：①②③三条确定性一次全过（同一 t 双截帧 / 换 seek 路径 / 静态 lint），
  而且 当时的机器验收 的 `[NOTE]`（它 grep `.textContent|innerText|innerHTML =`）
  **根本不会触发** —— 这条 `[NOTE]` 是给「DOM 里有每帧改文本」的方案提的醒，
  本方案没有这种代码。README 这里写清原因，免得复核时以为我漏看了这条。

`textW()` 用 `ctx.measureText` 现量现用（不缓存），只用于「光标 / 标签 / 框选的 x」，
并用 `Math.round` 落到整数像素，避免亚像素相位差。

### 2.2 逐字速率必须 **大于帧率**（否则自己给自己制造冻帧）

SPEC 给的是 `n = floor((t - t0) * cps)`。`cps` 不是随手写的：
30fps 下若 `cps < 30`，就有帧跨不出一个新字符 —— 相邻两帧**逐字节相同**，
`verify` 的密度指标上就是冻帧。取 `cps = 34`：

```
Δn/帧 = 34/30 = 1.133  →  floor 每帧至少 +1，永不为 0
```

代价是打字看起来很快（69 字 / 2.03s）。这是刻意的取舍：**逐字太慢 = 冻帧**，
而「慢速逐字」在 30fps 下只能靠加别的连续运动来补（variant-b 就是这么解决的，见 §3）。

输出行则用「横向刷出」：每行在自己的 `[t0, t0+0.200]` 里从 0 个字长到整行，
行与行**首尾相接**（`t1` 恰好等于下一行的 `t0`），所以输出段每帧都在变。
最长的一行 33 字，`0.200s = 6 帧` → 每帧涨 5.5 个字；最短的一行 11 字，每帧也涨 1.8 个字 ——
**都在 1 以上**，所以输出段也不会出现相同的两帧。

### 2.3 自动滚动是解析式，不是累加

```js
var scrollRows = Math.max(0, cur.row + 1 - VISIBLE);   // VISIBLE = 12
// 每行的 y = CY + (e.row - scrollRows) * LINE_H
```

19 行内容、12 行可视 → 末帧 `scrollRows = 7`。
「已占行数超过可视行数就顶上去」这一句自然语言，直接就是一个 `max`。
因为 `row` 是展开时就定好的字面量，滚动量只可能是 `t` 的函数。

### 2.4 光标方波：`Math.floor(t * 2) % 2`

```js
if (Math.floor(t * 2) % 2 === 0) {          // 亮：实心块
  ctx.fillStyle = C_ACC; ctx.fillRect(cx, cy - 12, 12, 24);
} else {                                     // 灭：空心框（仍是可读的「焦点」信息）
  ctx.strokeStyle = C_ACC_DIM; ctx.lineWidth = 2;
  ctx.strokeRect(cx + 1, cy - 11, 10, 22);
}
```

- 周期 0.5s，与 `t` 同源，seek 到任何时刻都得到确定的相位。
- **不能用** `animation: blink 1s infinite`：`infinite` 会让末帧闪回第 0 帧（反例 A4），
  而且 CSS 动画的相位不受 `t` 控制。
- 「灭」态画成空心框而不是消失：这样末帧（`t=4.9667` 落在灭态）仍是完整的结束构图，
  光标位置依然读得出来 —— 这是 §7.5「末帧成图」的细节。

### 2.5 光标跟着「打印头」走：同一个真值来源

输出阶段的方块光标不是停在命令行上，而是骑在**正在刷出的那一行的行尾**（像打印头）：

```js
var ci = (cur.kind === "pause" || cur.kind === "mark") ? prevTextIdx(i) : i;
var cx = CX + (ce.kind === "type" ? Math.round(textW(PROMPT)) : 0)
            + Math.round(textW(ce.text.slice(0, shown)));
var cy = CY + (ce.row - scrollRows) * LINE_H + LINE_H / 2;
```

行号（`ce.row`）、已显示字符数（`shown`）、滚动量（`scrollRows`）**全部来自同一次
`lineIndexAt(t)`**。停顿段 `cur.kind === "pause"` 时用 `prevTextIdx()` 往回找最近一条有文字的条目 ——
于是停顿时光标就停在命令行行尾，与「没有新字符」严格一致（§3.3 的 md5 证据）。

### 2.6 variant-b：把「逐字」这一个原语单独放大（块宽是连续量）

variant-b 的块宽不能是「整字数 × 字宽」——那样字与字之间块宽不变，同样会冻帧。
做法：块宽在**两个字之间线性插值**（连续），文本仍按整字揭示（离散）。

宽度表在 load 时一次量出，播放期只查表（`evidence/measure-probe.html` 拍下来的实测）：

```
line 1  font-size 72px   chars 13   CJK 13
  measured full width  = 945.375px
  letter-spacing       = 0.72px / 字
  平均每字             = 72.721px
  扣掉字距后的 CJK advance = 72.001px = 1.0000em      ← 与 n×em 的理论值完全吻合
```

`evidence/measure-readout.png` 就是这张取证图的截帧。三条结论：

1. CJK 逐字 advance 恰为 1em（差异全部来自 `letter-spacing` 与西文比例字形）；
2. 所以「拆字累加 == 整串测量」，逐字宽度表可以**预计算**，播放期不必再量；
3. 文本用 `clip-path: inset(0 <右侧裁掉 px> 0 0)` 揭示整字，**永不改文本内容** ——
   绕开 §6.1 的第二个办法（不动字，只动裁切）。

## 3. 三方案对比

| | **主方案 index.html**（终端回放） | **variant-a**（编辑器逐行） | **variant-b**（打字机 + 高亮块） |
|---|---|---|---|
| 谁来画 | 整幅 `<canvas>`（窗口/文本/光标/框选） | DOM：17 个 `<div>` + 行号 + minimap | DOM：2 行大标题 + 块 + 光标 + 标尺 |
| 逐字/逐行原语 | `floor((t-t0)*cps)` + 二分 | 整行出场：`opacity` + `translateY` 7px | 文本 `clip-path` 整字揭示 + 块宽插值 |
| 每帧写什么 | canvas 全量重绘（不碰 DOM） | 每行 `opacity` / `transform` / minimap `opacity` / 状态栏条宽 / `clip-path` | 2 处 `clip-path`、2 处块宽、条宽、光标 left/top/height/opacity |
| 信息密度 | **高**（19 行 × 40+ 列，回放感） | 中（17 行代码 + 语法色 + minimap） | **低**（2 行大字，留白最多） |
| 每帧成本 | 19 次 `fillText` + 几十次矢量绘制，很轻 | 约 55 次 style 写入（不触发布局，只触发重绘） | 约 12 次 style 写入，最轻 |
| 成片体积 | 387 KB | 268 KB | **125 KB** |
| 中文能否是豆腐块 | 不能（`Noto Sans Mono CJK SC` 已装） | 不能（等宽 CJK） | 不能（`Noto Sans CJK SC` 比例字形） |

**推荐主方案 `index.html`**，理由是「三个都过 determinism，但只有它同时把
①密集可变文本 ②自动滚动 ③光标跟随 ④框选几何 四件事压在同一次二分结果上」，

variant-a 的价值是证明「同一套时间表换成 DOM 逐行出场也成立」，并且信息密度接近主方案、
体积小 30%，是「要真编辑器质感」时的首选；variant-b 是把原语抽出来做对照实验的产物，
观感最干净但内容最少，单独出片略显单薄。

## 5. 踩坑记录

### 1. 逐字速率与帧率同频会制造冻帧（一开始没意识到）

第一版想让打字「看得清」，取了 `cps = 24`。算一下：`24/30 = 0.8`，也就是每 5 帧里有 1 帧
跨不出新字符 —— 这些帧逐字节相同。5s 里有近 1s 是打字段，白送 ~8 个冻帧对。
改成 `cps = 34`（> 30）后打字段**一帧都不重复**。这条不影响契约合规，
但直接影响 `verify` 的密度读数，属于「数值选择要先算一遍」的教训。

### 2. 起手静止壳的最后一帧会「白送」一个冻帧

`t=0.26` 开始打字，但帧落在 `t = k/30` 上：`t=0.2667` 时 `floor((0.2667-0.26)*34) = 0`，
画面与上一帧完全相同 —— 静止壳从 8 帧变成 9 帧。这类「常数没对齐帧格」的偏移
在 30fps 下很容易踩到，调 `T_TEXT` 时顺手算一下 `(k/30 - T_TEXT) * cps >= 1`。
本次没改（13% 静止占比已达标），但记录在此，免得下一个人以为是别的原因。

### 3. 输出行用「整行淡入」会有尾部重复帧

`opacity = 0.15 + 0.85 * easeOut(u)`：`easeOut` 在 `u→1` 时变化极小，
最后两帧的透明度差 < 1/255，**量化后是同一帧**。改成横向刷出
（`floor(u * 字数)` 每帧涨 5 个字）后，每帧差异是几十个像素，彻底没有这个问题。

### 4. variant-b 的「块宽 = 整字数 × 字宽」会冻住

第一版块宽跟着整字数跳。6.3 cps 下每个字之间约 4.7 帧完全不动 —— 又是冻帧。
改成「块宽在两个字之间线性插值、文本按整字揭示」：块边缘每帧移动 ~15px（连续），
字符仍是量子化落下的（离散）。这个「连续量 + 离散量」的组合反而比纯逐字更有打字机感。
顺带把校验写进了 `window.__measure`，再用 `evidence/mk-measure-probe.mjs` 拍图取证（§2.6）。

### 5. `letter-spacing` 会污染「拆字累加 == 整串测量」的校验

取证页第一版直接拿 `measured - CJK数 × em` 当误差，报出 9.375px 的「偏差」，
看起来像字体度量不可预测。实际是 `.h1` 上的 `letter-spacing: .01em`：
13 个字 × 0.72px = 9.36px，正好等于那个「偏差」。扣掉字距后 advance = 72.001px = 1.0000em。
**教训：做度量校验时要把自己的 CSS 也当成变量算进去**，否则会得出「字体不可信」的错误结论。

### 6. 框选标签不能放在框外上方

框选块顶部就在可视区顶部（末帧滚动 7 行），框外上方没空间；一开始把它放在
`boxTop - 30`，直接压在命令行文字上。改成**放在框内右上角**：第一行输出只有 ~300px 宽，
右上角 700px 是空的，标签放进去刚好，而且「已选中」三个字紧贴选区，语义更顺。

### 7. 中文逐字宽度在比例字体下不齐（variant-b 的 `任意 t 用…`）

副标题里有 3 个西文字符（` t `），在 `system-ui → Noto Sans CJK SC` 这条栈里走的是
**比例字形**（实测 3 个字符共 24.75px，不是 3×30px 的等宽）。所以逐字宽度表**必须实测**，
不能拿 `n × em` 糊过去 —— 这也正是「预计算宽度表」比「按字数算」更值得写的原因。

### 场景仪表与合片（§7.6）

主方案里唯一的「仪表」是框选标签的文字 `已选中 8 行输出`，
它由 `"已选中 " + OUTS.length + " 行输出"` 生成，和实际画出的输出行数**同源**，
不存在「一个说完成、另一个说 99%」的可能；也没有第二个进度条。

**若以后要把多个特效 concat 成整片**：本特效的画面里没有跨段进度条，可直接拼。
但框选标签里的 `8` 是本段内部的计数，如果整片要插手画之外的进度指示，
应当改走 kit 的 `gbar.json` + `REEL.offset`，不要在这里另起一条时间线。
